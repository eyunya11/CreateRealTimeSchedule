# Createの列車を、現実と同じ長さの1日で動くダイヤで走らせる

> 状態: ドラフト v0.7 ／ 対象: Minecraft 1.21.1・NeoForge 21.1.262・Create 6.0.10 以上 ／ ライセンス: MIT

Create の時刻表は「1日20分」の時間に縛られていて、実際の鉄道のような分刻みのダイヤ(列車の運行計画)は組めない。CreateRealTimeSchedule は、現実と同じ速さで進む1日24時間の時計を Minecraft に足し、その時計で列車の出発時刻を決める待機条件を Create に追加する。空の昼夜もその時計に合わせる(設定で無効にできる)。列車が遅れたときは停車時間を詰めて、元のダイヤに戻るようにする。

そのうえで第2段階として、所要時間の計算、運用(どの列車をどの順に走らせるかの割り当て)、ダイヤグラム(運行図)、遅れが大きいときの運転整理、待避を足したい。第2段階は、所要時間の計算(M4)、ダイヤどおりの運行(M5)、ゲーム内の運行図(M6)、ブラウザでのダイヤの編集(M7)、運休でダイヤに戻す運転整理(M8)、列車を待つ待避と緩急接続(M9)まで実装した。

このメモでは、すでに決めたことと、まだ決めていないことを分けて書く。

決めたことは四つある。時計は tick を基準にする(`gameTime + offset`)。想定するのは24時間動くサーバーで、時刻の調整はコマンド、テストには `/tick rate` を使い、時計だけの倍率は持たない。空は既定で時計に合わせ、設定で無効にできる。遅れは停車時間を詰めて回復する。

決めたいのは二つある。Create Dispatcher の部品を使うかどうかと、周期つきの時刻で最初の停車の枠をどう決めるか、である。ダイヤの編集方式は、ブラウザで開く Web ページに決めた(M7)。Create Train Next の制限速度標識の意味(単位、向き、範囲)は、Create Train Next の側で決まった。

## 扱う範囲

第1段階で作るのは、時計、空の同期、時刻表の待機条件、遅れの回復の四つである。列車の走り方(加速、信号の挙動、経路選択)には手を入れない。出発のタイミングだけを変える。

第2段階は構想で、実現可能性の調査までしてある。あえて扱わないものは、スロットルを上げて遅れを取り戻す回復運転、駅の案内板、時計ブロックである。

## 背景: Createの時刻条件は、1日20分の時間に縛られている

Create の「時刻」待機条件は、ワールドの昼夜の時間(day time)を読む。1日は24000 tick で、現実の20分にあたる。1000 tick が1時間で、朝6時が0 tick である。設定画面で「7時15分」と選んでも、現実の7時15分とは関係がなく、ゲーム内の1時間は現実の50秒にすぎない。現実で3分かかる駅間を走るあいだに、ゲーム内の時刻は3.6時間も進む。

成立の幅も狭い。この条件は、目標の時刻から40 tick(2秒)以内でしか真にならず、逃すと次の周期まで待つ。昼夜の時間はベッドで寝ても `/time set` を使っても動くので、ダイヤの基準としては安定しない。

「8:10発、8:25発、8:40発」のような運行を、遅れの扱いまで含めて組みたい。出発点はそこにある。

## 提案: 現実と同じ速さの時計と、その時計で出発を決める待機条件

### 時計は gameTime に offset を足して作る

時計の値は `gameTime + offset` とする。20 tick が1秒、1分が1200 tick、1日が1,728,000 tick で、バニラの昼夜の72倍の長さになる。

```
clockTicks = gameTime + offset                  // 時計の絶対値(long)
day        = floorDiv(clockTicks, 1,728,000)    // 何日目か
timeOfDay  = floorMod(clockTicks, 1,728,000)    // その日の0時からの tick
保存       = オーバーワールドの SavedData に offset だけ
```

offset はワールドごとに保存する。クライアントは offset を受け取るだけでよく、表示は `gameTime + offset` から計算する。世界を作った時点の時刻は設定で決められる(既定は6:00)。他の MOD が時計を読めるよう、`RealClock` を取得するメソッドを公開する。

基準を現実の壁時計(サーバーの時刻)にする案とは、次の軸で比べた。

| 軸 | tick基準(`gameTime + offset`) | 壁時計(サーバーの時刻) |
| --- | --- | --- |
| 列車の動きとの整合 | 同じ tick で進むのでズレない | サーバーが遅れると列車だけ遅れる |
| 一人用でポーズしたとき | 時計も列車も止まる | 時計だけ進む |
| サーバー停止中 | 止まり、再開後もつながる | 進み続け、再開時に時刻が飛ぶ |
| 現実の時刻との一致 | TPS が20を下回ると遅れる | 常に一致する |
| 実装 | offset を保存するだけ | タイムゾーンなどの設定が要る |

tick基準を採る。時計の役目は列車の運行を決めることで、現実の時刻と一致させることではない。時計が刻むのは現実の秒ではなく「ゲーム内の秒」であり、`/tick rate` で tick の速さを変えれば時計も同じだけ速くなる。

想定する運用は、24時間動き続けるサーバーである。その場合、時計は現実の時刻とほぼ同じ速さで進む。ただし時計はサーバーが動いている間しか進まないので、再起動や停止の分だけ現実の時刻から遅れる。遅れはコマンドで直す。

- `/rtclock get`: いまの時刻と日数を表示する。
- `/rtclock set <時:分[:秒]>`: 時刻を設定する。日付は変えない。
- `/rtclock align`: サーバーの現実の時刻に合わせる。前後12時間以内でいちばん近いその時刻へ時計を動かすので、日付が変わることがある。

`align` は日付を変えてよい。23:00 に止めたサーバーを翌日の 01:00 に起動して合わせると、時計は2時間進んで翌日の 01:00 になる。日付を変えずに 01:00 にすると、時計は22時間戻り、その日の運用のうち、もう列車を割り当てたものは翌日まで走らない。設定の `align_on_start` も同じ合わせ方をする。

(コマンド名は仮。)時刻を進めれば、待機中の列車はすぐ出発し、戻せばその分長く待つ。ダイヤの時刻が基準だからである。一人用で遊ぶ場合、時計は遊んでいる間しか進まない。夜のダイヤを見たいときは `set` で合わせるか、`/tick rate` で全体を速くする。時計だけを速くする倍率は持たない。列車の走行時間と時計の秒が食い違い、ダイヤの意味が変わるためである。

### 空は時計に合わせる。設定で無効にできる

Minecraft の空の見た目は、既定で時計に合わせる。設定(`sync_sky`)で無効にでき、無効のときはバニラの昼夜に戻る。

方式は、ゲームルール `doDaylightCycle` を false にして、毎 tick にオーバーワールドの昼夜の時間を時計から設定する、というものにする。

```
dayTime = floorDiv(clockTicks, 72) + 18000
```

バニラの昼夜の時間は、0 が朝6時にあたる。この式だと、時計の12:00が正午(6000)、0:00が真夜中(18000)になる。日数も昼夜の時間に反映されるので、月の満ち欠けは現実の1日ごとに進む。

この方式にした理由は、NeoForge 21.1.262 のコードを読んで確かめた点にある。1.21.1 では、昼夜の時間が自然に進むのも、全員が寝たときに夜がスキップされるのも、`doDaylightCycle` が true のときだけである。false にしておけば、寝ても夜は飛ばず、時計と空がずれない。`/time set` を使われても、次の tick で時計の値に戻る。

注意点は五つある。

- 空が現実と同じ速さになるので、夜は現実の夜と同じだけ続く。寝て夜を飛ばすことはできない。
- 同期を有効にした時点の `doDaylightCycle` の値を保存し、無効にしたときに元へ戻す。有効の間に誰かが true に戻しても、毎 tick に値を確かめ、違うときだけ書き直す。
- 昼夜の長さを変える他の MOD(例: Better Days)とは併用できない。併用するなら `sync_sky` を無効にする。
- クライアントには、バニラの仕組みで1秒に1回、昼夜の時間が送られる。空が動くのは3.6秒に1 tick ぶんなので、見た目への影響はない。
- MOD を外すと、ゲームルールを戻す者がいなくなり、`doDaylightCycle` は false のまま残る。外す前に `sync_sky` を false にして一度起動するか、外したあとに `/gamerule doDaylightCycle true` を実行する。

NeoForge 21.1 には、昼夜の進む速さそのものを変える API(`setDayTimePerTick`)もある。ただし、確認できた範囲では、その値をクライアントへ送る仕組みがバニラの通信に含まれていない。今回は採らなかった。

### 待機条件 `real_time_of_day`

設定の項目は、Create の時刻条件(`TimeOfDayCondition`)と同じ、時・分・周期にする。周期の選択肢も同じ(24・12・6・4・3・2・1時間、45・30・15分)で、現実の時間として読む。追加する設定は「最短停車時間」だけで、新しい条件の既定は20秒にした。

この条件は、Create の時刻条件を継承せず、`ScheduleWaitCondition` から直接作った。継承すると、時刻条件を型で見分ける他の MOD に、同じものとして読まれるおそれがある。Create 本体には、そうした箇所はない(ソースを検索して確かめた)。設定画面で条件ごとに使える行は1行(幅およそ121ピクセル)なので、時刻、最短停車時間、周期をその1行に詰めた。

出発時刻の規則は一つの式で書ける。

```
D = max(T, A + M)

A: 列車が駅に着き、この条件の評価が始まった時刻(時計の絶対値)
T: この列車が出るべき出発枠(時計の絶対値)
M: 最短停車時間
D: 実際に出発する時刻(時計の絶対値)
```

早く着けば T まで待ち、遅れて着けば最短停車だけして出る。単純な規則である。D は待機を始めた時点で一度だけ計算し、列車のデータ(条件ごとに保存される領域)に書く。以降は毎 tick に時計と比べるだけである。時計の絶対値で持つので、`/rtclock set` で時刻を動かしても、待機中の列車は新しい時刻に従う。サーバーを再起動しても、offset が保存されているので崩れない。

出発枠 T は、到着の時刻ではなく、列車がその前に使った枠につなげて決める。前の停車で使った枠 P があれば、T は P より後で、この停車の設定時刻(と周期)に最初に一致する時刻とする。遅れた列車は定刻の枠を過ぎているので、すぐに出発し、以降の停車でも、時刻表に追いつくまで最短停車で走る。同じ時刻の条件が1周で2回現れる線でも、2回目は前の枠より後の、翌日の枠を取るので、その場で出発してしまうことがない。

つなげた枠が、到着から周期1つぶんより離れているときは、つなげずに数え直す。過去に離れている列車は、枠をたどるかぎり、ほかの列車より1周期以上遅れたままで、最短停車で走り続ける。未来に離れているのは、時計を戻されたときで、たどると何時間も待たされる。数え直しは、次に書く最初の停車と同じで、到着に最も近い枠を取る。15分周期の線で、1つ前の停車の枠が 8:10、この停車の設定が 8:13 の列車が 8:40 に着いたとき、つなげた枠の 8:13 は27分前で、1周期(15分)を超える。数え直すと 8:43 になり、列車は 8:43 まで待つ。1日周期の線では、1日以上ずれたときにだけ数え直すので、数時間の遅れは、枠を保ったまま回復する。

前の枠がない最初の停車だけは、到着に最も近い枠(同じ距離なら後ろ)を T とする。列車ごとの「前の枠」は、Create の条件の領域が停車のたびに消えるため、列車の ID をキーにして SavedData に保存する。保存するのは待機を始めたときで、出発のときではない。時刻表が差し替わったときは捨てる。差し替わったかどうかは、時刻表の中身(いま何番目の停車にいるかを除く)から計算した値で見分け、同じ中身の時刻表を入れ直したときは、つづきとして扱う。同じ停車の「または」の列に時刻の条件が2つあるときは、どちらも同じ前の枠からつなげる。

この条件は時刻表に保存され、クライアントにも送られる。そのため、Create 6.0.10 以上が必須で、サーバーにもクライアントにも本 MOD が要る。M1 では時計の通信路を任意にしていたが、必須に改めた。本 MOD を持たないクライアントは、入れているサーバーに入れないはずである(接続はまだ試していない)。

### 遅れは、停車時間を詰めて回復する

出発枠が 8:10、最短停車時間が30秒、定刻の到着が 8:08 の駅で、到着が遅れた場合を並べる。

| 到着 | 状況 | 出発 | 停車時間 | 出発の遅れ |
| --- | --- | --- | --- | --- |
| 8:08:00 | 定刻 | 8:10:00 | 2分00秒 | なし |
| 8:09:00 | 1分遅れ | 8:10:00 | 1分00秒 | なし(回復) |
| 8:11:00 | 3分遅れ | 8:11:30 | 30秒 | 1分30秒(一部回復) |

回復できる量は、予定の停車時間から最短停車時間を引いた分までである。それを超える遅れは次の駅に持ち越される。駅間の走行に余裕があれば、そこで残りを取り戻せる。余裕がなければ遅れは減らないが、増え続けることもない。つまり、ダイヤを組む側が駅間に余裕を持たせておく設計になる。

遅れの原因は、信号待ち、駅の混雑、スロットルの設定などである。プレイヤーが乗っているときに限り、進行方向のチャンクが読み込まれるまで列車が止まる場合もある。どれも列車の走りの側の事情で、本プロジェクトは出発の判断だけを受け持つ。

## 第2段階の構想と、実現可能性

ここから先は構想である。Create の開発版(6.0.11 を準備中のもの)のソースを読み、必要な API がアドオンから呼べることを、作業用のコピーでのコンパイルで確かめた。読んだ `content/trains` 以下(列車と時刻表のクラス)は 6.0.10 のリリースと同じ内容で、コンパイルも 6.0.10 でやり直して通した(「確認できたことと、まだのこと」の表を参照)。列車を実際に動かして確かめたのは、所要時間の計算だけである(次の節)。

### 所要時間は速度の上限から計算できる

列車の速さは、サーバーの設定値と簡単な式で決まる。最高速度は28ブロック/秒、カーブでは14ブロック/秒、加速と減速はどちらも3ブロック/秒²で、いずれも設定で変わる。燃料で動く列車は別の値になる。スケジュールのスロットルの命令は、最高速度に掛かる割合になる。停止するときは、距離 v²/2a の手前から減速し、駅の手前10ブロックでは速度を絞る。カーブの手前では、あらかじめ減速する。

計算は、Create の速度制御(`Navigation.tick`)を1 tick ずつ再現して行う(`TravelTime`)。5000ブロックの区間でも数千回の繰り返しで済むので、時刻表のすべての駅間で呼んでよい。実際の列車と比べると、5つの場合のどれも、tick 単位まで一致した。

| 駅間 | スロットル | 実際の列車 | 計算 |
| --- | --- | --- | --- |
| 20ブロック | 全速 | 96 tick(4.80秒) | 96 tick |
| 40ブロック | 全速 | 133 tick(6.65秒) | 133 tick |
| 40ブロック | 1/4 | 154 tick(7.70秒) | 154 tick |
| 40ブロック | 1/10 | 298 tick(14.90秒) | 298 tick |
| 300ブロック | 全速 | 382 tick(19.10秒) | 382 tick |

最初は、始点から加速し、終点と上限の手前から減速した速さの小さいほうを取る、なめらかな計算(速度の包絡線)で見積もる案だった。実際の列車との差は、300ブロックで0.55秒あった。1 tick ずつの計算のほうが実際に近く、手間も問題にならないので、包絡線は採らなかった。

また、最初の再現には誤りがあった。列車は駅の0.25ブロック先を目指して走るが、駅の印に届いた tick で止められる。再現は、その0.25ブロック先まで数えていたので、実際より10 tick(0.5秒)長く出た。実際の列車を測って、初めて分かった。

直線で信号のない区間なら、最高速度に達するのに131ブロック・9.3秒かかり、止まるにも同じだけかかる。262ブロック以上の区間では、所要時間はおよそ「距離 ÷ 28 + 8.6秒」になる(上の誤りを直す前は 9.3秒としていた)。

| 距離 | 所要時間 |
| --- | --- |
| 500ブロック | 約26秒 |
| 1000ブロック | 約44秒 |
| 5000ブロック | 約187秒 |

止まる手前では、減速の判定が tick ごとに入れ替わる。そのため、距離が1ブロック違うだけで、所要時間が最大9 tick(0.45秒)増減する。5〜3000ブロックを全速で走る場合を、1ブロックずつ計算して測った値である。実際の列車も同じようにゆらぐので、どんな見積もりにも、この程度の誤差は残る。

駅間の距離は線路グラフの辺の長さを足して求め、カーブの辺かどうかも辺ごとに判定できる。信号待ちや混雑は計算に入らない。それを含めた予測には、Create Dispatcher のシミュレーターのような仕組みが要る。

区間の途中にカーブがあるときは、上限つきの区間(`SpeedZone`)として計算に渡す。先頭が区間の中にいる間は上限を超えず、手前では、上限に届くように減速を始める。減速を始める距離は、上限を u として (v² − u²) / 2a で、Create がカーブの手前で使っている規則と同じ形である。Create Train Next の制限速度の標識は、手前の減速の規則が少し違うので、区間とは別に渡す(次の節)。

カーブを含む区間は、tick 単位では合わない。カーブの上では、Create は台車の前後の車輪の直線距離を一定に保つように、毎 tick 車輪の位置を直す。そのたびに、先頭の車輪が、列車の数えている距離から0.1〜0.3ブロックほど前後にずれる。列車は、残りが320、220、120ブロックのところで道を探し直すときに、このずれを残りの距離に取り込む。最後の探し直しより後のカーブだと、ずれは駅まで残る。先頭が前にずれていれば早く着き、後ろにずれていれば、数えている距離が尽きても停止位置に届かない。その場合、列車は Create が行き過ぎた列車に与える遅い速さで残りを進むので、十数 tick 遅れる。止まる手前の Create の制御は、1ブロックの違いで最大9 tick 変わるので、わずかなずれでも到着が数 tick 動く。ずれ方は線路がワールドのどこにあるかで変わり、同じ線路でも走らせるたびに違う。S字カーブと90度のカーブを、別の場所に置いた写しも含めて約150回走らせると、計算との差は8 tick 早いから17 tick 遅いまでで、たいていは6 tick 以内だった(0.3秒以内)。17 tick 遅れたのは、90度のカーブをスロットル1/2で走った1回だけである。計算はこのずれを入れていない。1000ブロックの区間では、計算は次のようになる。

| 条件 | 所要時間 |
| --- | --- |
| 制限なし | 約44秒 |
| 400〜700ブロックに、上限11.2ブロック/秒の区間 | 約64秒 |
| 400〜700ブロックに、上限5.6ブロック/秒の区間 | 約93秒 |
| 全線に、上限11.2ブロック/秒の区間 | 約93秒 |
| 400ブロックに 40 km/h(11.1ブロック/秒)の標識、700ブロックに解除標識 | 約65秒 |

### Create Train Next の制限速度標識を、所要時間に含める

Create Train Next(同じ作者の別プロジェクト)には、制限速度の標識がある。所要時間の計算は、この標識を上限の列に加える。

標識は、Create の線路グラフの上の点(`EdgePointType` の独自の種類 `createtrainnext:speed_limit`)として保存され、値は `getLimit()` で読める。グラフの点なので、サーバーにもクライアントにも同期され、所要時間の計算から読める。

読み方は二つ確かめた。どちらもコンパイルまでで、確かめたのは、値がまだ最高速度に対する割合(%)だったころの版である。

- 直接読む: Create Train Next を compileOnly の依存にして、`graph.getPoints(CTNEdgePointTypes.SPEED_LIMIT)` で標識を取り、`getLimit()` と辺の上の位置を読む。
- ID で読む: 依存を持たず、`EdgePointType.TYPES` から `createtrainnext:speed_limit` を引き、値をリフレクションで読む。Create Train Next が入っていないワールドでは何も起きない。

標識の意味は、強制を実装する Create Train Next の側で決まった。以下は、Create Train Next の PR #9(`feature/speed-limit-kmh`)の仕様で、ソースの `TrainSpeedLimits` と `SpeedLimitEdgePoint` で確かめた。PR #9 は、2026年10月19日に既定のブランチ `mc1.21.1-neoforge` へマージされている。走行中の列車に上限を強制するのも、この PR からである。

| 項目 | Create Train Next の仕様 |
| --- | --- |
| 単位 | km/h。1ブロック/秒を 3.6 km/h とする。値は 1 から、Create の設定の最高速度(`trainTopSpeed` と `poweredTrainTopSpeed` の大きいほう)の3.6倍まで(既定の設定では144)。置いたばかりの標識は40 |
| 向き | 標識が向いている向きに走る列車にだけ効く(`appliesTo` が `isPrimary` を見る)。駅の進入方向と同じ扱いである |
| 範囲 | 標識の地点から、次の標識まで。上限は列車ごとに保存され、駅を越えても続く |
| 解除 | 専用の解除標識(`track_speed_release`)を使う。解除標識は、上限を最大値に戻す |
| 0 | ない。いちばん低い値は 1 km/h |
| 減速 | 先読みして、`Train.maxSpeed()` を √(L² + 2ad) に抑える。L は標識の速度、a は列車の加速度の0.8倍(Create は減速にも加速と同じ値を使う)、d は列車の先頭から標識までの距離から1ブロックを引いたもので、標識の1ブロック手前で標識の速度に届く。先読みするのは、最高速度からのブレーキ距離に30ブロックを足した先までで、止まっている列車は先読みしない |
| 信号 | 五現示の信号が、現示ごとに上限をかける(警戒 25、注意 45、減速 75 km/h。設定 `signals.*` で変えられる)。上限は次の信号まで続き、進行の現示で解かれる。標識の上限とは別に持ち、列車は小さいほうに抑えられる |

標識の値は、3.6 で割ってブロック/秒に直す。上限は `Train.maxSpeed()` の中でかかり、Create の `Navigation.tick` は、その値にあとからスロットルを掛ける。列車の速さは、最高速度、標識、信号、先読みのうち最も小さいものに、スロットルを掛けたものになる。たとえばスロットル 50% の列車は、40 km/h の標識の区間を 20 km/h で走る。km/h は絶対的な速度なので、燃料のある列車も、燃料のない列車も、同じ速度に抑えられる。

`Train.maxSpeed()` は、Create Train Next がその時点の上限まで下げるので、`TrainSpecs.of` は、所要時間に渡す列車の最高速度を Create の設定から読む(燃料のある列車は powered の値)。

`TravelTime` は標識を、上限の区間とは別に受け取る。渡すのは、標識の列(`SpeedSign`)と、出発時に効いている上限である(`SpeedSigns`)。毎 tick、Create Train Next の `TrainSpeedLimits.cap` と同じ順で上限を求め、Create の `Navigation.tick` と同じく、その値を駅の10ブロック手前からの減速に使い、そのあとでスロットルを掛ける。カーブの上限はスロットルを掛けたあとの速さにかかるので、ここが区間との違いである。

- 減速の規則: 標識の手前では、カーブとは違い、減速度の0.8倍で、標識の1ブロック手前に上限へ届くように抑える。先読みする距離も Create Train Next と同じにした。
- 持ち越す上限: 標識の上限は駅を越えて続く。区間の終わりに効いている上限は `SpeedSigns.limitAfter` で求まるので、次の区間はそれを出発時の上限として計算する。運行の見込み(`Forecast`)も編集ページも、列車の停車の順に上限を渡していく。列車ごとに、最初の駅では上限がないものとする。折り返す駅では、両方向に標識を置く使い方を前提にしているので、前の列車からは持ち越さない。編集ページは書き出しの区間の `curves` と `signs`、ネットワークの `train` から、`TravelTime` と同じ計算(`travel.js`)で、上限を持ったまま出る列車の所要時間を求める。区間の `ticks` は丸める前の距離から計算してあるので、丸めた距離で計算し直さず、`ticks` に上限がある場合とない場合の差を足す。`TravelTime` と `travel.js` が同じ tick を出すことは、共通の走りの例(`travel/cases.json`)で、Java と Node の両方から確かめている。
- 駅の先の標識: Create Train Next の先読みは、Create の信号の先読みと同じく、経路の終わりの先まで線路をたどる(分岐では最初の選択肢を選ぶ)。駅のすぐ先に遅い標識があれば、列車は駅の手前から減速する。100ブロックの区間で、駅の5ブロック先に 10 km/h の標識があると、所要時間は10.9秒から14.85秒に延びる。書き出しも、駅の先は同じ向きにたどる。経路の終わりの先では、Create は分岐でグラフの順の最初の行き先を選び、信号の向きは見ないので、それに合わせた。

信号の現示による上限はそのときの他の列車の位置で決まるので、線路だけを見る見積もりには入らない。そこで、ダイヤの列車を定刻どおりに、同じ時計で1 tick ずつ一緒に走らせる再現(`Traffic`)を作った。各列車は `TravelTime` と同じ速度制御(`Drive`。`TravelTime` はこれを駅まで走らせる)で走り、信号は Create の `Navigation` と同じに扱う。ブレーキ距離を3の倍数に切り上げた先までの信号を見て、通る信号の先の閉塞区間を予約し、ほかの列車がいるか予約された閉塞区間の手前の信号では止まり、空くまで待つ。駅では、4.5ブロック以内の信号が赤なら出ない。Create の連動信号はその先の連動でない信号の閉塞区間まで空いていなければ通さない。列車がふさぐのは、先頭から列車の長さだけ後ろまでのあいだにある閉塞区間で、交差する閉塞区間も一緒にふさぐ。着いた駅の停止位置ちょうどにある信号は、区間の書き出しと同じく、通ったものとする。Create Train Next があれば、通った信号の現示の速度に、次の信号まで抑えられる。現示は先の空いた閉塞区間の数(分岐では最も少ないほう)を、頭の現示の数で決まる梯子に当てて決める。Create の信号を通ると、その上限は解ける。先の信号の現示に向けた先読みの減速も、標識と同じ規則で入れた。ゲームの灯は0.5秒ごとに現示を決め直すが、再現では毎 tick 決める。

列車を動かす順は Create と同じにした。Create は信号を待っている列車を待ち始めた順に先に動かし、そのあとで、走っている列車を、走り出した(待つのをやめた)順に動かす。同じ tick に同じ閉塞区間を取り合えば先の列車が取るので、待たされた列車は次の tick に先に予約し、今度はもう一方が待たされる。加速中の2本が同じ閉塞区間を交互に取り合うこともある。

ダイヤからは、運用ごとに1組の編成として、運用に入らない列車は1本ずつ走らせる(`TimetableTraffic`)。編成は最初の駅の発車の時刻に現れ、各駅をダイヤの時刻に、遅れて着けば最短停車のあとに出る。列車は全速で走り、長さはダイヤに書いた値、なければ設定の値とする。運用の編成は車庫に戻ったあと、その日のあいだ車庫に止まって閉塞区間をふさぐ。運用に入らない列車は、ダイヤにその先がないので、終点で線路から下ろす。標識と信号の上限は駅をまたいで持ち越し、列車ごとの最初の駅では上限がないものとする。駅の手前の列車の体は前の区間の上にあるものとし、最初の駅では、そこで立っている閉塞区間だけをふさぐ。線路にない区間があれば、その編成はそこから先を走らない。10分を超えて遅れた列車は、線路から下ろす。線路が通せる数を超えるダイヤで、列車が限りなく積み重ならないようにするためである。駅で下ろした列車は、出るはずだった区間を、着かなかった区間として返す。何も動かないあいだは時計を先へ進めるが、赤で止まったままの列車を下ろす時刻より先へは進めない。後ろで待つ列車が、その列車が下りたあとに動けるようにするためである。区間は駅名の組ごとに1つなので、どの列車も駅の同じホームに入る。Create なら空いたホームに入るが、再現にはホームの選び方を入れていない。そのため、1本が止まっているホームに次の列車が来る車庫や終着駅では、再現だけ赤で待つか、着かないことになる。再現は、列車と区間ごとに、かかった tick、線路だけの所要時間との差、赤で止まった信号と秒数を返す。運行の見込みは、列車が出る call の列車と、その列車の何番目の停車かで、再現の区間を引き、信号で延びた分を線路の所要時間に足す(`RunTimes.signalTicks`)。再現は線路の事実(`TrackFacts`)を読んだあと、見込みに初めて要るときに一度だけ走らせ、線路かダイヤが変わるまで持つ。列車の速さは燃料のない列車の全速、最短停車時間と列車の長さはサーバーの設定の値である。

再現は手で組んだ線路網の単体テストで確かめた。止まっている列車の後ろを走る列車は、信号の場所に同じ速度の標識を置いたのと同じ tick になる(五現示と六現示。六現示の進行の 130 km/h は、燃料のある列車で効く)。赤の信号で止まった列車は、先の列車が線路から下りた次の tick に出る。単線の区間で向かい合う2本は順に通り、互いの閉塞区間に立つ2本はどちらも着かない。連動信号では、その手前で待つ。分岐の先では、空いた閉塞区間の最も少ない枝で現示を数え、交差する閉塞区間に列車がいれば、その手前の信号で止まる。現示の速度、赤での停止、列車の長さ、連動信号、交差、分岐の数え方、上限の持ち越し、終点に止まること、列車を動かす順、10分の打ち切り、停止位置の信号、駅で下ろした列車の区間、下ろす時刻までの時計の進め方を、それぞれ外すと、対応するテストが落ちることも確かめた。18時間に2160本(30秒ごと)を走らせても、1秒かからない。

再現は Create Train Next を入れたゲームテスト(`SignalTrafficTests`)で、実際の2本の列車とも比べた。五現示の灯式信号機を40ブロックおきに5つ置いた線路で、40ブロック先の駅に止まっている列車と、後ろの列車が同時に出発する。2本は加速しながら最初の信号の先の閉塞区間を取り合い、後ろの列車は警戒、減速、注意、警戒の現示で走って、空いた線路なら333 tick のところを601 tick かかった。再現も601 tick で、2回とも tick 単位で一致した。最初の再現は487 tick と出た。列車を動かす順を Create と同じにして512 tick になり、前の列車が終点に止まり続けるようにして601 tick になった。再現から現示の速度を外すと、このテストは落ちる。

編集ページは、同じ再現を `traffic.js` に写して使う。`travel.js` の速度制御も、`Drive` と同じ1 tick ずつの形に直した。Java と JS が同じ結果になることは、共通のケース(`traffic/cases.json`。手で組んだ線路網の走り16件と、ダイヤ3件)を、Java(`TrafficCasesTest`)と Node(`traffic.test.js`)の両方で走らせて確かめている。ページは、ダイヤが変わるたびに、読み込んだネットワーク第5版の閉塞区間でダイヤの列車を走らせ、信号で延びた tick を、列車の区間の所要時間に足してから秒に切り上げる。ドラッグのあいだは、ドラッグを始めたときのダイヤの結果を使う。線路の所要時間より短いという注意、ドラッグと時刻の入力の制限は、この所要時間で決まる。注意は、信号で延びた秒数も示す。赤の信号で止まる列車は、どの信号(前の駅からのブロック数)で何秒止まるかを注意に出し、10分を超えて止められる列車も注意に出す。サーバーの最短停車時間は、ページからは分からないので、設定の既定の20秒とする。列車の長さは、ダイヤの値か、ページの設定の値である。

再現が重くなりすぎないように、列車を動かした回数が500万回を超えたら、再現をやめる(`Traffic.MAX_STEPS`)。列車が走っているあいだ、1 tick に1回と数えるので、1分ごとに2分ずつ走る列車が1日に1080本あっても、107万回ほどである。線路が通せる数を大きく超えるダイヤでは、数十本の列車が10分ずつ止められ、数十秒かかっていた。やめたときは、どの列車の結果も使わない。編集ページは、信号を入れた所要時間を求めきれないことを注意に出し、線路の所要時間だけで見る。

強制(Create Train Next の側)と所要時間の計算(こちら)は、別々に書かれている。同じ走りになるかは、Create Train Next を入れたゲームテスト(`SpeedSignRunTests`)で、実際の列車と比べて確かめた。300ブロックの区間で5通りを走らせ、所要時間は5通りとも計算と tick 単位で一致した(「確認できたことと、まだのこと」の表)。Create Train Next にはリリースも公開の Maven もないので、ビルドした jar を `libs/createtrainnext.jar` に手で置いたときだけ、このテストを登録する。git は `libs/` を含めず、CI では走らない。

### ダイヤグラムは「見る」と「作る」を分けて考える

ダイヤグラムは、横軸が時刻、縦軸が駅で、列車が斜めの線になる図である。

見る機能は、ゲーム内の画面で作れる。駅の並び(路線)は Create に無いので、本プロジェクトで定義する。駅同士の距離は線路グラフから求まり、列車の位置もサーバーが持っているので、計画の線と実績の点を重ねて描ける。線の描画は自前で行う。1.20.1 では Create Dispatcher が、シミュレーション結果から時間–距離図を描いており、同種の実績がある。

作る機能は、図に線を引いて、そこから運用と時刻表を生成するものである。編集の置き場所は、四つの案を比べた。

| 方式 | ライブデータ | 複数人 | 編集のしやすさ | コスト |
| --- | --- | --- | --- | --- |
| デスクトップアプリ | なし | 各自が導入 | 高い | 配布と保守が別に要る |
| ゲーム内 | あり | 向く | 低い | 文字入力、ドラッグ、拡大縮小を自作する |
| MOD 組み込みの Web 画面 | あり | 認証が要る | 高い | 鍵、ポート、別の技術。Create Dispatcher の方式 |
| 静的 Web ページ + JSON の貼り付け | なし | 向く | 高い | 小さい |

専用のデスクトップアプリは採らない。ワールドを直接読めず、サーバーでは全員が導入する必要があるためである。先にダイヤのデータ形式(JSON)を決め、ゲーム内は図の表示と運行の確認に使い、編集はブラウザで開く静的な Web ページで行うことにした(「ダイヤの編集ページ(M7)」の節)。ゲームとは、クリップボードとファイルで JSON をやりとりする。ライブデータが欲しくなったら、組み込みの Web 画面を足す。

### 運行図(M6)

運行図は、運行中のダイヤの1つの路線を、ゲーム内の画面に描く。`/rtdiagram` で最初の路線を、`/rtdiagram line <路線>` で指定した路線を開く。キーでも開ける。キーは、最初はどれにも割り当てていないので、操作の設定で割り当てる。見るだけなので、権限は要らない。

- 横軸は時刻、縦軸は路線の駅である。駅の間隔は、Create の線路の長さ(ブロック)で決める。隣り合う2駅の間は、路線のほかの駅を通らない道のうち、短い方の長さにする。向きは問わない。周回する線路で、ほかの駅を回って戻る道を、駅の間隔と取り違えないためである。線路でつながらない間は、ほかの間の平均にする(どの間も分からなければ100ブロック)。
- 環状線(`"loop": true`)は、先頭の駅を下にもう一度置く。列車が下へ進むか上へ進むかは、線路が示す回り方で決める。2駅の間のいちばん短い道が、途中の路線の駅を片方の回り方でだけ通るなら、その回り方である。線路が示さない区間は、停車の並びから、通る駅の少ない方の回り方にする。同じなら下へ進む。先頭の駅をまたぐ区間は、下の端までと上の端からの2本の線に分け、その区間にかかる時間を、2本の長さの比で振り分ける。
- ダイヤの列車は細い線で、種別の色で描く。色は、ダイヤの `types` で種別に決めた色で、決めていない種別は、名前から編集ページと同じ計算で選んだ色になる。途中の停車で種別が変わる列車は、その停車に止まっている線から先を、新しい種別の色で描く。回送は灰色の点線である。列車番号は、始発の点に、始発の種別の色で添える。
- 運用の実績は、太い赤の線で重ねる。中断した運用は紫にする。駅に止まっている列車の線は、いまの時刻まで横に伸ばす。走っている列車の線は、最後に出た駅で止める。いまどこを走っているかの推定は、まだしていない。ただし、待ちの相手として見張っている駅を止まらずに通った列車は、通った時刻を記録しているので、実績の線をその駅で折り、走っている列車の線もそこまで伸ばす。長い列車では、先頭が次の駅に着いてから最後の車両が駅を過ぎることがある。その通過では折らない(折ると線が時刻を戻る)。路線の外を走った区間の通過も使わない。駅と駅をまっすぐ結ぶと、遅れて駅の手前までゆっくり走り、そこから速く走った列車が、実際より早く駅を通ったように見えるからである。
- ダイヤの待ち(`wait_for`)は、点線の矢印で描く。待たれる列車がその駅を出る(通る)ところから、待つ列車が出るところへ向ける。決め方は編集ページと同じで、同じ場合を Java と Node のテストで確かめている。その日に運休した列車や、どの運用にも入っていない列車がかかわる待ちは、MOD が待たないので、薄く描く。待たれる列車が、待つ列車の発車の時刻より後に出る(通る)ダイヤでは、矢印は時刻を戻る向き(右から左)になる。待つ列車が、自分の時刻を過ぎて待つことになる、という印である。
- ホイールで時刻の方向に拡大縮小し、ドラッグで動かす。ホイールは1ノッチで約1.08倍(1.25 の3乗根)に拡大縮小し、3ノッチで1.25倍になる。初めは1ノッチで1.25倍だったが、速すぎたので3分の1にした。タッチパッドや、1ノッチより細かく回せるホイールで、ノッチの途中まで回したときは、回した分だけ拡大縮小する。編集ページの運行図と地図、地図の画面の「地図で選ぶ」の地図も、同じ速さにする。左右の矢印キーで路線を、Page Up と Page Down で前日と当日の営業日を切り替え、Home でいまの時刻に戻る。開いたときは、いまの時刻の前後2時間を出す。0時を過ぎても前日の営業日の運用が走っているあいだは、前日を出す。
- 画面を開いているあいだ、クライアントは1秒ごとにサーバーへ問い合わせる。サーバーは、だれが画面を開いているかを覚えない。覚えるのは、1人に最後に答えた時刻だけで、答えるのは0.5秒に1回までにする。改造したクライアントが問い合わせを繰り返しても、ダイヤを何度も送らないためである。ダイヤの JSON と駅の間隔は、クライアントの持っている版が古いときだけ送る。運用の実績も版の番号を持ち、運用が始まった、駅を出た、着いた、終わった、記録を捨てたときにだけ送り直す。クライアントは、サーバーと同じコードで JSON を読み、運用の停車の並びを組み立てる。大きな通信は NeoForge が分けて送るので、400万文字までのダイヤを送れる。それより長いダイヤは送らず、画面にその旨を出す。
- 実績を描けるように、サーバーは、終わった運用と中断した運用の到着と発車の時刻を、いまの営業日と前日の分だけ保存しておく。ダイヤを読み直したとき、停車の並びが変わった運用の記録は捨てる。`/rttimetable unload` では、すべて捨てる。
- 駅の間隔は、最初に問い合わせがあったときに線路から求め、ダイヤを読み直すまで使い続ける。道を探すのは、ダイヤの路線の駅からだけで、線路網のすべての駅からではない。運転整理の所要時間と、待ち合わせの相手も、同じく線路から求めたものを使う。線路が変わったときは、自動で求め直す。サーバーは1秒ごとに線路網の指紋(ノード、線路のつながりと長さ、駅とその名前、信号、標識)を取り、それが変わってから5秒変わらなければ、線路を読み直す。線路を敷いているあいだは、何度も読み直さない。路線の軸が変わったときだけ、クライアントに送り直し、待ち合わせの相手も求め直す。`/rtdiagram refresh`(権限レベル2)は、すぐに求め直す。

### ダイヤの編集ページ(M7)

編集ページは、ブラウザで開く Web ページで、運行図に線を引いてダイヤを作る。ページは2か所から開ける。

- MOD の jar に入っているページ。クライアントのコマンド `/rteditor` が、ゲームフォルダの `createrealtimeschedule/editor/` に取り出して、既定のブラウザで開く。毎回上書きするので、ページの版はいつも MOD の版と同じになる。
- GitHub Pages で公開するページ(`https://eyunya11.github.io/CreateRealTimeSchedule/`)。jar のものと同じファイルで、main に変更が入るたびに公開し直す。MOD を入れていない人も使える。

ページは、ふつうの `<script>` で読むファイルだけでできていて、ビルドの手順も外部のライブラリもない。`file://` で開いたページは ES モジュールを読めないためである。同じファイルを、Node のテスト(`src/test/js`)が `require()` で読む。

ゲームとのやりとりは、クリップボードかファイルで行う。クリップボードのコマンドは、どれもクライアントのコマンド `/rteditor` の下にある。クリップボードを読み書きするのは、プレイヤーが自分でこのコマンドを打ったときだけで、サーバーからは読むことも書くこともできない。サーバーのコマンドにすると、オペレーターが `/execute as` でほかのプレイヤーとして実行し、その人のクリップボードを読めてしまうからである。サーバーは、権限レベル2のプレイヤーのクライアントから来たものだけを受け付ける。

- `/rteditor copy network`(権限レベル2)は、`/rtnetwork export` と同じ線路の JSON を、実行したプレイヤーのクリップボードに写す。クライアントは合言葉を付けてサーバーに頼み、10秒のうちに同じ合言葉で返ってきたものだけをクリップボードに置く。ページの「線路を読み込む」に貼り付けると、駅の一覧と、駅の間の所要時間を使える。
- `/rteditor copy timetable`(権限レベル2)は、運行中のダイヤを写す。ページの「ダイヤを開く」に貼り付けて直せる。
- ページの「書き出す」でクリップボードに写し、ゲームで `/rteditor paste`(権限レベル2)を実行すると、そのダイヤで運行を始める。クライアントがクリップボードの中身をサーバーに送り、サーバーは権限を確かめてから読み込む。読み込みは `/rttimetable load` と同じ処理で、誤りがあれば断って理由を出す。NeoForge が大きな通信を分けて送るので、400万文字までのダイヤを貼り付けられる。
- ファイルでも受け渡せる。ページで保存したファイルを、ワールドフォルダの `createrealtimeschedule/timetable.json` に置いて `/rttimetable load` を実行する。

ページでできることは、次のとおりである。

- 路線を作る。駅は、読み込んだ線路の駅から上から順に選ぶか、名前を打ち込む。環状線の印も付けられる。
- 運行図は、ゲームの運行図(M6)と同じ規則で描く。縦軸の駅の間隔は線路の長さで、環状線の扱いも同じである。縦軸と線の作り方のコードを、そのまま JavaScript に移した。
- 「列車を描く」を押してから駅の行をクリックしていくと、列車ができる。最初のクリックが始発の発車になる。次の駅には、前の駅の発車に線路の所要時間(tick を20で割って切り上げた秒)を足した時刻に着く。それより右をクリックすれば、クリックした時刻に着く。着いた駅には、その駅の停車時間だけ止まる。着いたあとマウスを右へ動かすと、発つ点がマウスについてくる。同じ駅の行をもう一度クリックすると、そこで発つ。ボタンを押したままにしなくてよい。発つ時刻を決めずにほかの駅の行をクリックすると、停車時間だけ止まって発つ。描いている欄で、その列車の停車時間を決めると、それから描く駅では、発つ時刻をクリックで決めないかぎり、どこでもその時間だけ止まる。描いた停車の停車時間は、その欄の表でも直せる。直すと、後ろの停車も同じだけずれ、駅の間の所要時間は変わらない。時刻は、ふだんは15秒ごとに、Shift を押している間は5秒ごとに揃える(どちらの刻みも設定で変えられる)。ダブルクリックか Enter で描き終え、列車番号は自動で振る。
- 停車時間と最短停車時間は、駅ごとに「駅の停車時間」で決める。停車時間は、線を引くときと回送を足すときに、その駅で止まる時間で、決めていない駅は設定の値(既定は20秒)になる。最短停車時間は、遅れた列車がその駅で最低限止まる時間で、決めていない駅はサーバーの設定 `default_minimum_stop_seconds` になる。列車ごとには、右の欄の表で、停車ごとに停車時間(着いてから発つまで)と最短停車時間を直せる。停車時間が最短停車時間より短い停車には印を付ける。遅れていなくても、列車が遅れて出るからである。時刻の刻みも、設定で変えられる。
- 選んだ列車の着く点をドラッグすると、到着の時刻だけが動き、発車はそのままなので、停車時間が変わる。始発と終点のように時刻が1つの停車は、その時刻が動く。発つ点をドラッグすると、停車時間が伸び縮みし、後ろの停車も同じだけずれる。駅の間を走る線をドラッグすると、その区間だけが、所要時間を保ったまま動き、両端の停車時間が変わる。停車している線をドラッグすると、列車全体が時刻の向きに平行に動く。途中で停車しない列車は、Ctrl を押しながら走る線をドラッグして動かす。ドラッグで動かした時刻は、時刻の刻み(既定は15秒、Shift を押している間は5秒)に揃える。所要時間などの限りで止まるときも、限りの内側のいちばん近い刻みに止める。点や走る線をドラッグしている間は、動かしている区間を線路の所要時間で走ったときの線(前の駅を発ってから最短で着く線)を、赤い破線で出す。ポインターのそばには、動かしている時刻(着く点なら到着と停車時間、走る線なら発車と到着)を出す。列車番号、種別、回送の印、運休しない印(「大きな遅れは、運休でダイヤに戻す」の節)、停車の駅と時刻は、右の欄の表で直せる。Delete で列車を消す。
- 描いたあとで時刻を動かしたり直したりするときも、駅の間は線路の所要時間より短くできない。閉塞区間の入った線路では、この所要時間に信号の分も入る(「Create Train Next の制限速度標識を、所要時間に含める」の節)。点のドラッグはそこで止まり、表に打ち込んだ時刻は、前後の停車と所要時間が許すいちばん近い時刻に直して、そうしたと伝える。到着は発車より後にできず、発車は到着より前にできない。線路を読み込んでいないときは、前の駅を出たあとに着くことだけを守る。線路を読み込んだあとで所要時間より速く走る列車(先に描いた列車や、停車の駅を変えた列車)は、誤りの一覧の下に注意として出す。ゲームはこれを理由に断らない。
- 運用は、列車を順にクリックしてつなぐ。前の列車の終着駅から、着いたあとに出る列車のうち、まだどの運用にも入っていないものを候補として示す。「車庫との回送を足す」は、車庫から最初の列車の始発駅へ行く回送と、最後の列車の終着駅から車庫へ戻る回送を足す。行きの回送は、最初の列車の発車より、その駅の停車時間だけ前に着き、戻りの回送は、最後の列車が着いて、その駅の停車時間がたってから出る。線路に所要時間がない区間には足さず、そう伝える。
- 種別は、「種別」の画面で、色と並びを決める。色は、7色の見本から選ぶか、パレットで選ぶか、`#rrggbb` の形で書く。一覧には、色を決めた種別のあとに、列車が使っていて色を決めていない種別を、名前から選んだ色で並べる。この画面で何か変えるまで、ダイヤに `types` は書かないので、第5版までのダイヤは、開いて保存しても版が変わらない。名前を変えると、その種別の列車と停車も変わる。列車が使っている種別を消すときは、確かめてから、列車と停車から外す。列車の欄と線を引くときの欄の種別は、一覧の名前から選べ、新しい名前も書ける。停車の行の「ここから種別」で、その停車から先の種別を変える。線は種別の色で描き、途中で種別が変わる列車は、そこから色を変える。選んだ列車の点も、その停車の種別の色で描く。
- 誤りは、ゲームと同じ規則と同じ文言で、変更のたびに一覧に出す。Java の `Timetable.problems()` を JavaScript に移したもので、17個の共通のテスト用ダイヤ(`src/test/resources/.../timetable/cases`)を Java と Node の両方のテストが読み、同じ結果になることを確かめている。ダイヤの JSON の書き出しも、Java と一字一句同じになる。ただし、ページは同じ項目が二度ある JSON も読めてしまう(ブラウザの JSON の読み手は、後のほうを採る)。ページが書き出す JSON に、そういう重なりはない。
- 元に戻すとやり直すができる。作業中のダイヤと線路はブラウザに保存し、ページを開き直しても残る。`file://` で開いたページと GitHub Pages のページでは、保存先が別になる。
- 画面の言葉は日本語と英語で、ブラウザの言語に合わせて始まる。誤りの文言は、ゲームと同じく英語である。
- 停車ごとに、待つ列車を決められる(「待避と緩急接続(M9)」の節)。右の欄の停車の行で、列車と、その列車が出る(通る)駅を選んで足し、最長の待ち時間も決められる。運行図では、待つ相手が駅を出る(通る)ところから、待つ列車が出るところへ、点線の矢印を描く。
- 中央の欄の上で、運行図と地図(「線路の地図」の節)を切り替える。地図は、縦横に拡大と移動ができ、選んだ路線の駅を強調する。上の「表示する路線」で路線を選ぶと、その路線の列車が通る線路だけを濃く描き、ほかの線路は薄く描く。何も選ばなければ、全部の線路を濃く描く。「表示するもの」で、駅、駅名、信号、制限速度、列車を、それぞれ出すか出さないか決められる。「表示するタグ」では、「タグなし」とワールドのタグを、それぞれオンかオフにする(「線路の地図」の節の「表示するタグ」)。この選択はダイヤには書かず、ページの設定に保存する。信号と列車は、書き出したときの様子である。線路をクリックすると、右の欄で、左で選んだ路線の地図に足すか除くか、どの地図にも出さないかを決められる(ダイヤ第8版の `map_add`、`map_remove`、`map_hidden`)。どれも元に戻せる。ダイヤが、地図にない線路を指しているときは、下の一覧に注意として出す。地図つきの線路網は大きくなりうるので、下書きとは別に保存する。保存できないほど大きいときは、ページを開いているあいだだけ持つ。
- ページが読める形式の版(ダイヤは第9版、ネットワークは第5版まで)を画面に出す。それより新しい版の JSON は読まずに、ページの更新が要ると出す。GitHub Pages のページと MOD の版がずれても、読み違えないためである。

### ダイヤの JSON 形式(第9版)

ダイヤは、路線(駅の並び)、列車、運用の3つと、駅ごとの停車の時間と、種別の色と、地図に載せる線路を、1つの JSON にまとめる。M5 の運行も、ゲーム内の運行図(M6)も、ブラウザでの編集(M7)も、この JSON を受け渡しに使う。読み書きと検証は `timetable` パッケージにあり、Minecraft にも Create にも依存しない。次の例は、テスト用の `example.json` と同じ内容で、同じかどうかをテストが確かめている。

```json
{
  "format": "createrealtimeschedule.timetable",
  "version": 2,
  "name": "Central Line, weekdays",
  "lines": [
    {
      "id": "central",
      "name": "Central Line",
      "stations": ["Central Depot", "Central 1", "North Gate", "Harbor"]
    }
  ],
  "trains": [
    {
      "number": "D101",
      "line": "central",
      "deadhead": true,
      "stops": [
        {"station": "Central Depot", "depart": "08:02"},
        {"station": "Central 1", "arrive": "08:06"}
      ]
    },
    {
      "number": "101",
      "line": "central",
      "type": "local",
      "stops": [
        {"station": "Central 1", "depart": "08:10"},
        {"station": "North Gate", "arrive": "08:25", "depart": "08:26"},
        {"station": "Harbor", "arrive": "08:41"}
      ]
    },
    {
      "number": "102",
      "line": "central",
      "type": "local",
      "stops": [
        {"station": "Harbor", "depart": "08:50"},
        {"station": "North Gate", "arrive": "09:05", "depart": "09:06"},
        {"station": "Central 1", "arrive": "09:21"}
      ]
    },
    {
      "number": "D102",
      "line": "central",
      "deadhead": true,
      "stops": [
        {"station": "Central 1", "depart": "09:25"},
        {"station": "Central Depot", "arrive": "09:29"}
      ]
    }
  ],
  "duties": [
    {
      "id": "1A",
      "depot": "Central Depot",
      "trains": ["D101", "101", "102", "D102"]
    }
  ]
}
```

決めごとは次のとおりである。

- `format` と `version` は必須である。読み手は、自分が読める版より新しい `version` を見ると、ほかの項目を読まずに「MOD の更新が要る」とだけ返す。版を上げるのは、項目を足すなど、古い読み手が読み違える変更のときだけにする。
- 駅の名前は、Create の駅の名前と一字一句同じにする。列車は名前で駅へ向かうからである。
- 路線(`lines`)は、駅の並びだけを持つ。Create には駅の並びがないので、運行図の縦軸としてここで決める。環状線は `"loop": true` と書く。
- 列車(`trains`)は、1本の路線を走る1回の運行である。列車番号は文字列で、ほかの列車と重ならない。`stops` の最初の駅は発車(`depart`)だけ、最後の駅は到着(`arrive`)だけを持つ。途中の駅は発車が必須で、到着は省ける。`type`(各駅停車、快速など)は表示のための文字列で、省ける。運行図では、種別の色で線を描く。
- 回送の列車は `"deadhead": true` を持つ(第2版で足した)。客を乗せずに、車庫と運用の始まりや終わりの駅の間を走る列車で、ほかの列車と同じく運行図に線として描き、時刻で動かす。途中の駅は止まらずに通ってよい。第1版のダイヤも読め、回送の列車はないものとして扱う。ただし、次の運用の車庫の規則は第1版にも当てはまり、車庫に戻らない運用を含む第1版のダイヤは断られる。第1版の運用を走らせるものはそれまでなく、車庫に戻らない運用は運行できないからである。
- 時刻は `HH:MM` か `HH:MM:SS` の文字列で、ダイヤの開始日の0時からの経過を表す。日をまたぐ運行は、印刷された時刻表と同じように `24:10`(翌日の0時10分)と書く。書けるのは `47:59:59` までで、日付は持たない。
- 運用(`duties`)は、1組の車両の1日の仕事である。車庫の駅と、列車番号の並びを持つ。並びの次の列車は、前の列車が着いた駅から、着いたあとに出る。最初の列車は車庫から出て、最後の列車は車庫に着く(第2版で足した規則。車庫と運用の始まりの駅が違えば、間を回送でつなぐ)。
- 駅ごとの停車の時間は `stations` に書く(第3版で足した)。駅の名前(`name`)と、停車時間の秒数(`dwell`)と、最短停車時間の秒数(`minimum_stop`)を持ち、どちらの時間も省ける。駅は、どれかの路線の駅で、1回だけ書く。停車時間は、編集ページが線を引くときにその駅で止まる時間で、運行は読まない。列車がどれだけ止まるかは、停車の到着と発車の時刻が決めるからである。最短停車時間は、遅れた列車がその駅で最低限止まる時間である。
- 停車も `minimum_stop` を持てる(第3版で足した)。その列車のその停車だけの最短停車時間で、駅の値より優先する。最後の停車は発車しないので、持てない。運用の中で、前の列車の終着と次の列車の始発をまとめた停車では、次の列車の始発の停車の値を使う。
- 秒数は0から600までの整数である(サーバーの設定 `default_minimum_stop_seconds` と同じ上限)。例は次のとおりで、テスト用の `example-stop-times.json` と同じ内容である。Java と Node の両方のテストが、これを読んで一字一句同じに書き出すことを確かめている。

```json
"stations": [
  {"name": "A", "dwell": 30, "minimum_stop": 15},
  {"name": "B", "dwell": 45},
  {"name": "Depot", "minimum_stop": 0}
],
```

```json
{"station": "M", "arrive": "08:03", "depart": "08:03:30", "minimum_stop": 10}
```

- 列車は `"keep": true` を持てる(第4版で足した)。遅れた列車をダイヤに戻すときにも運休しない列車で、終電などに付ける(「大きな遅れは、運休でダイヤに戻す」の節)。例は、テスト用の `example-keep.json` にあり、Java と Node の両方のテストが、一字一句同じに書き出すことを確かめている。
- 停車は `wait_for` を持てる(第5版で足した)。発つ前に待つ列車の並びで、それぞれ列車番号(`train`)と、その列車が出る(止まらずに通る)駅(`at`。省けば停車の駅)と、自分の発車の時刻から待つ最長の秒数(`max_wait`。0〜3600。省けばサーバーの設定)を持つ。例: `"wait_for": [{"train": "3001", "at": "S1"}, {"train": "2", "max_wait": 120}]`。待つ列車は、ダイヤのほかの列車で、その駅を出るか通るかし、それがこの停車の発車より厳密に前でなければならない。こうしておけば、待ち合いが輪になることはない。どの駅を通るかは路線の並びで決める。環状線では、どちら回りかは線路で決まり、ダイヤだけでは分からないので、2つの停車の駅のほかは、どの駅も通りうるとする。走らせるときは、運行図の軸と同じく線路から回り方を決める。最後の停車は発車しないので、持てない。例は、テスト用の `example-waits.json` にあり、共通のテスト用ダイヤ `cases/waits.json` で、Java と Node が同じ誤りを出すことを確かめている。
- 種別の色は `types` に書く(第6版で足した)。それぞれ名前(`name`)と色(`color`。`#` と16進の6桁)を持ち、並びは編集ページで種別を並べる順である。同じ名前は2回書けない。例: `"types": [{"name": "local", "color": "#3a9d5d"}, {"name": "rapid", "color": "#d9822b"}]`。列車や停車の種別が `types` にないときは、名前から7色の見本のうちの1つを選ぶ。選び方は Java の `String.hashCode` を7で割った余りで、編集ページも同じ計算をするので、ゲームと編集ページで同じ色になる。
- 停車は `type` を持てる(第6版で足した)。その停車から先の、列車の種別である。その停車に止まっているあいだも、その種別とする。例: 各駅停車が途中の駅から快速になる `{"station": "S", "arrive": "08:04", "depart": "08:05", "type": "rapid"}`。最後の停車は発車しないので、持てない。例は、テスト用の `example-types.json` にあり、共通のテスト用ダイヤ `cases/types.json` と `cases/types-shape.json` で、Java と Node が同じ誤りを出すことを確かめている。
- 列車と停車は `tag` を持てる(第7版で足した)。列車を走らせる線路のタグ(「線路のタグ(M10)」の節)の名前である。列車の `tag` はその列車のすべての駅間に効く。停車の `tag` はその停車から次の停車までの駅間だけ、列車の `tag` に代わる。種別と違い、その先の駅間には続かない。空の文字列は指定がないことを表し、停車では列車の `tag` に従う。最後の停車は発車しないので、持てない。例はテスト用の `example-tags.json` にあり、共通のテスト用ダイヤ `cases/tags.json` と `cases/tags-shape.json` で、Java と Node が同じ誤りを出すことを確かめている。
- 地図に載せる線路は、線路の鍵(「線路の地図」の節)の並びで書く(第8版で足した)。路線は `map_add` と `map_remove` を持てる。その路線を映す地図は、路線の列車が通る線路に `map_add` の線路を足し、`map_remove` の線路を除いて描く。車庫への線路を足したり、通らない側線を除いたりするためである。最上位の `map_hidden` の線路は、どの地図にも描かない。全部の線路を映すときも描かないので、作りかけの区間を隠すのに使う。同じ並びに同じ線路は2回書けず、1つの路線で同じ線路を足しながら除くこともできない。鍵が地図にない線路を指していても誤りにはしない。線路を延ばすと鍵が変わるので、編集ページは地図にない鍵を注意として出す。例は、テスト用の `example-map.json` にあり、共通のテスト用ダイヤ `cases/map.json` で、Java と Node が同じ誤りを出すことを確かめている。
- 列車は `length` を持てる(第9版で足した)。列車の長さで、1〜10000 の整数のブロックである。灯式信号機の現示を見積もる再現(「Create Train Next の制限速度標識を、所要時間に含める」の節)で、列車がふさぐ閉塞区間を求めるのに使う。書かない列車は、ゲームではサーバーの設定 `train_length_blocks`、編集ページでは設定の値(どちらも既定は40ブロック)の長さとする。編集ページの列車の欄は、1〜10000 の整数でない長さを受け付けず、そう出す(-1 は長さなしと読めてしまうため)。設定の長さの欄を空にすると、40ブロックに戻る。例はテスト用の `example-length.json` にあり、共通のテスト用ダイヤ `cases/length.json` と `cases/length-shape.json` で、Java と Node が同じ誤りを出すことを確かめている。
- 書き出すときは、そのダイヤを書ける最も古い版にする。長さを持つ列車があれば第9版、なければ、地図に載せる線路を足すか除くか隠していれば第8版、なければ、線路のタグを持つ列車か停車があれば第7版、なければ、種別の色か、種別を変える停車があれば第6版、なければ、待つ列車があれば第5版、運休しない列車があれば第4版、駅ごとの時間か停車の最短停車時間があれば第3版、どれもなければ第2版で書く。第2版までしか読めない MOD にも、第2版のダイヤは渡せる。
- まだ持たないものは、スロットルの指定、周期のある時刻(「15分おき」)、通過の時刻、曜日ごとのダイヤである。足すときは版を上げる。

読み手は厳しくする。手で書いたり、ほかのツールから貼り付けたりした JSON の間違いを通すと、あとで「列車が走らない」という形で出てくるからである。コメント、単引用符、引用符のない名前、末尾のカンマ、末尾より後ろの文字は誤りにする。同じ項目を二度書いたときも、形式にない項目や型の違う値があるときも誤りにする。形が正しければ、中身も確かめる。路線にない駅、路線の並びに逆らう停車(環状線は除く)、時刻が逆戻りする列車、つながらない運用などである。誤りは、見つかったものをすべて、JSON の中の場所をつけて返す(50件まで)。ダイヤは全体が受け入れられるか断られるかのどちらかで、一部だけ読むことはしない。

### ネットワークの書き出し

ダイヤを作る側(M7 の編集ページ、M6 の運行図)は、どんな駅があり、駅の間を列車が何 tick で走るかを知る必要がある。コマンド `/rtnetwork export`(権限レベル2。名前は仮)は、Create の線路グラフを読み、ワールドの `createrealtimeschedule/network.json` に書き出す。`/rteditor copy network`(権限レベル2)は、同じ内容を、実行したプレイヤーのクリップボードに写す(「ダイヤの編集ページ(M7)」の節)。形式は次のとおりで(第2版。第1版に `signs` を足した。線路のタグがあるワールドでは第3版で書く。下で述べる)、例は線路の上に一直線に並べた3駅を書き出したものである。同じ内容のテスト用の `example.json` と同じかどうかを、テストが確かめている。

```json
{
  "format": "createrealtimeschedule.network",
  "version": 2,
  "train": {"topSpeed": 28, "turnSpeed": 14, "acceleration": 3, "throttle": 1},
  "stations": ["Alpha", "Beta", "Gamma"],
  "legs": [
    {"from": "Alpha", "to": "Beta", "distance": 20, "ticks": 96},
    {"from": "Alpha", "to": "Gamma", "distance": 40, "via": ["Beta"], "ticks": 133},
    {"from": "Beta", "to": "Gamma", "distance": 20, "ticks": 96}
  ]
}
```

- `stations` は駅の名前である。同じ名前の駅(ホームが複数ある駅など)は1つにまとめる。時刻表は駅を名前で呼ぶからである。
- `legs` は、駅 `from` の停止位置に止まっている列車を、駅 `to` へ送り出したときに走る道である(選び方は下)。名前の組ごとに1本で、線路が一方通行なら逆向きの組はない。同じ名前どうしの組は作らない。
- `distance` はブロック単位の道のり(小数第2位まで)、`ticks` は `train` の速さとスロットルで止まらずに走り通したときの所要時間で、20 tick が1秒である。所要時間は、丸める前の距離から計算する。信号待ちと他の列車は入らない。計算できないとき(スロットルが0など)、`ticks` は書かない。
- `via` は、その道の途中で止まらずに通過する駅で、順に並べる。`curves` は、道のうちカーブの区間を、`from` からの距離の `[始点, 終点]` で並べたもので、`ticks` の計算に使われる。どちらもなければ書かない。
- `signs` は、道で出会う Create Train Next の制限速度標識(列車の進む向きを向いたもの)を、`from` からの距離 `at` と上限の `kmh` で並べたもので、解除標識は `kmh` の代わりに `"release": true` を持つ。例: `"signs": [{"at": 400, "kmh": 40}, {"at": 700, "release": true}]`。駅 `to` の先の標識も、512ブロックまでにあれば入れる。分岐では、Create が経路の終わりの先で選ぶ行き先(グラフの順で最初のもの)をたどる。列車は駅に入る途中でも、それに備えて減速するからで、その `at` は `distance` より大きい。標識がなければ(Create Train Next がないときも)書かない。
- `ticks` は、出発のときに標識の上限がかかっていない列車の値である。前の区間から上限を持ち越した列車は、この区間の最初の標識まで遅くなる。区間の終わりに効いている上限は、`at` が `distance` 以下の最後の標識で決まる。標識のない区間は、持ち越した上限をそのまま残す。編集ページは上限を持ち越した列車の所要時間を、`distance`、`curves`、`signs`、`train` から自分で求める(「Create Train Next の制限速度標識を、所要時間に含める」の節)。
- `train` は、燃料のない列車の速さ(最高速度、カーブでの速度、加速。ブロックと秒の単位)と、スロットル(いまは全速の1)である。サーバーの設定をそのまま使う。

第3版はワールドに線路のタグかタグのブロックがあるときだけ使い、どちらもなければ第2版のまま書く。第3版で足したものは次のとおりである。`tags` にはワールドのタグの名前を並べる。`tagProblems` は区間の誤りで、`problem` が `junction`(区間が分岐に着く)か `mixed`(2種類のブロックが混ざる)、`block` がブロックの座標、`other` が混ざった相手のブロック、`node` が分岐の位置を表す。`platforms` は駅の停止位置ごとの駅名で、配列の順がホームの番号になる。`legs` には、タグなしの駅間に続けて、タグごとの駅間(`tag` 付き)と、ワールドの一覧にないタグの列車の駅間(`"otherTag": true`)を並べる。`ways` は、各ホームに止まっている列車を各駅名へ送り出したときに着くホームで、`{"from": 1, "tag": "local", "to": {"B": 3}}` の形で書く。タグなしでは `tag` を省き、一覧にないタグでは `otherTag` を付ける。編集ページはこの `ways` を使って、「このタグでは道がない」を調べる。例はテスト用の `railway/example-tags.json` にある。

第5版は、線路に信号があるときに使い、閉塞区間(Create の `SignalEdgeGroup`)を足す。灯式信号機の現示と、信号が赤かどうかは、どの閉塞区間に列車がいるかで決まるので、所要時間に信号を入れる再現(`Traffic`)に使う。第5版は第3版のものをすべて持ち、地図はあれば入れる。地図を省いた第5版もある。閉塞区間には0からの番号を付け、`blocks` はその数である。`crossings` は、線路が交差する2つの閉塞区間の組で、片方に列車がいると、もう片方もふさがる。`signals` は、信号の向きごとの並びで、それぞれ列車が入る閉塞区間(`block`)と、その閉塞区間の先の信号(`next`。分岐があれば複数、線路が途切れればなし)を持つ。Create Train Next の灯式信号機があれば、その現示の数(`lights`。2〜6)を持ち、Create の連動信号なら `"cross": true` を持つ。`lightSpeeds` は Create Train Next の設定の現示ごとの速度(km/h)で、Create Train Next がなければ書かない。区間の `block` は出発のときに列車がいる閉塞区間、`signals` は途中で通る信号を、出発からの距離 `at` と信号の番号 `signal` で並べたもので、出発の停止位置の信号は通らず、到着の停止位置の信号は通るものとする。Create がまだ閉塞区間を求めていない線路は、2つのノードのあいだごとに1つの閉塞区間とみなし、そういう線路がいくつあったかをログに出す。例はテスト用の `example-signals.json` にあり、実際の線路で、閉塞区間と信号の並びが線路のとおりに読めることをゲームテストで確かめている。

道の選び方は、Create の経路探索(`Navigation.search`)に合わせた。線路は滑らかにつながる向きにだけ進み(`TrackEdge.canTravelTo`)、信号などの辺の点が通さない向きには進まない(`canNavigateVia`)。信号は、置いた向きに走る列車だけを通すので、反対向きの信号は線路を一方通行にする。どの辺でも、列車が入ったところ(出発する辺では、列車のいるところ)から見て最初の通さない点より手前の駅には行けるが、その点の先へも、その辺の先へも探索を進めない。周回線で、出発した辺に一周して戻ったときは、列車のいた位置より後ろを見ないので、同じ辺の後ろにある駅には行けない(別の辺なら、一周して行ける)。Create の探索はこのとおりで、どちらも実際の線路のゲームテストで、Create の列車がそう動くことを確かめた。直線の線路はチャンクの境目で辺に分かれるので、駅と同じチャンクの範囲に反対向きの信号や別の駅があると、これに当たる。書き出しは初め、出発する辺の信号を見落とし、のちの辺の信号の手前の駅には行けないとし、同じ辺の後ろの駅には一周して行けるとしていた。どれも実際の線路のゲームテストで見つかり、探索を直した。駅へは、Create が停車を許す向きからだけ入る(`canApproachFrom`)。道は、長さと重みの和がいちばん小さいものを選ぶ。重みは Create の探索と同じで、書き出しでは、途中で通る駅ごとの50だけが入る(列車のいる駅、赤信号、他の列車、列車ごとに使える線路の種類は、送り出すときにしか分からないので入れない)。探索は Minecraft にも Create にも依存しない `RouteSearch`(`RailNetwork` の上)で行い、運行で列車を送り出すときも同じ探索を使う(次の節)。Create の線路グラフから `RailNetwork` を作る `CreateNetwork` だけが Create を使う。Create Train Next の標識も `CreateNetwork` が読むが、依存は持たない。辺の点の種類は名前(`createtrainnext:speed_limit`)で引き、上限は `getLimit()` と `isRelease()` をリフレクションで読む。標識は、置いたときの向き(辺の1つ目のノードから2つ目へ)に走る列車にだけ効くので、その向きの辺にだけ付ける。

### 線路の地図

線路を上から見た地図を、編集ページとワールドの画面で見られるようにする。地図はワールドの X と Z の座標をそのまま使い、1ブロックを1単位とする実寸の地図で、高さは使わない。線路の形は、Create の線路グラフの辺を1本ずつ読んで作る。曲線はベジェ曲線の形のまま、約2ブロックごとの点で表す。辺は往復で2本あるが、地図では1本の線路にまとめる。

ネットワークの書き出しは、地図を入れると第4版になる。第4版は第3版のもの(線路のタグ、ホーム、`ways`)をすべて持ち、ワールドにタグがなくても書く。各区間の `tracks` は、タグごとの区間にも付く。第4版は、タグの色(`tagColours`)と、線路ごとのタグの区間、列車が走るタグも持つ。地図がなければ、これまでどおり第3版か第2版で書く。ゲームの書き出しには、いつも地図が入る。例は、上の3駅の線路の東の端から南へ曲がる線路を足し、信号、標識、列車を1つずつ置いたもので、テスト用の `example-map.json` と同じかどうかをテストが確かめている(`legs` などは上の例と同じなので省いた)。

```json
  "map": {
    "dimensions": ["minecraft:overworld"],
    "tracks": [
      {"key": "minecraft:overworld 0.5,2,3.5 60.5,2,3.5", "dimension": 0, "points": [0.5, 3.5, 60.5, 3.5]},
      {"key": "minecraft:overworld 60.5,2,3.5 70.5,2,13.5", "dimension": 0, "points": [60.5, 3.5, 66.4, 5.8, 68.7, 8.1, 70.5, 13.5]}
    ],
    "stations": [
      {"name": "Alpha", "track": 0, "x": 10.5, "z": 3.5},
      {"name": "Beta", "track": 0, "x": 30.5, "z": 3.5},
      {"name": "Gamma", "track": 0, "x": 50.5, "z": 3.5}
    ],
    "signals": [
      {"track": 0, "x": 40.5, "z": 3.5, "sides": [{"dx": 1, "dz": 0, "kind": "create", "lamps": ["G"]}, {"dx": -1, "dz": 0, "kind": "light4", "lamps": ["Y", "G"]}]}
    ],
    "speedLimits": [
      {"track": 0, "x": 20.5, "z": 3.5, "dx": 1, "dz": 0, "kmh": 60},
      {"track": 1, "x": 68.7, "z": 8.1, "dx": 0.71, "dz": 0.71, "release": true}
    ],
    "trains": [{"name": "Train 1", "carriages": [{"points": [25, 3.5, 16, 3.5], "tracks": [0, 0]}]}]
  }
```

- `dimensions` は、線路のある次元の名前である。
- `tracks` は線路で、`points` に X と Z を交互に並べる(小数第1位まで)。`dimension` は `dimensions` の何番目かである。`key` はダイヤが線路を指す名前で、次元と両端のノードの位置(低い方が先)から作る。Create の辺には長く続く名前がないからで、端の先に線路を延ばすと名前が変わる。坂の端のように、Create がノードを何ピクセルか持ち上げているときは、その端の後ろに `+8px` のように書く。同じ位置で高さの違うノードを、Create は別のものとして扱うからである。
- `stations`、`signals`、`speedLimits`、`trains` は、それぞれ駅の停止位置、信号、Create Train Next の制限速度標識、列車である。どれも `track` で、乗っている線路を `tracks` の何番目かで示す。表示する線路を選んだとき、その線路の上のものだけを出すためである。
- 信号の `sides` は、信号の頭がある向きごとの表示である。`dx` と `dz` はその向きに走る列車の進む向き、`kind` は Create の信号(`create`)か Create Train Next の灯式信号機(`light2` から `light6`。数字は現示の数)か、`lamps` は点いている灯の色を上から並べたもの(`R`、`Y`、`G`)である。書き出したときの表示なので、編集ページの地図は、その時点の様子になる。
- 制限速度標識の `dx` と `dz` は、標識が効く列車の進む向きである。上限は `kmh`、解除標識は `"release": true` を持つ。
- 列車の `carriages` は車両ごとの前と後ろの端の位置(`points`)と、それぞれが乗っている線路(`tracks`)である。
- 地図があるとき、`legs` の各区間は `tracks` を持つ。その道が通る線路を、通る順に `tracks` の番号で並べたものである。例: `"tracks": [0]`。
- 最上位の `tagColours` は、ワールドのタグの名前ごとの色(`#rrggbb`)である。例: `"tagColours": {"Local": "#3a9d5d"}`。
- 線路の `tags` は、タグのブロックの区間がかかる部分である。`from` と `to` は、線路の最初の点から測った長さの割合(0 から 1、小数第3位まで)で、`tags` はその部分のタグの名前を一覧の順に並べたものである。例: `"tags": [{"from": 0.4, "to": 1, "tags": ["Local"]}]`。両方向の辺の区間をまとめるので、一方向のブロックの区間も入る。区間のない線路は `tags` を書かない。区間は辺の長さの割合で求め、辺が線路の点と逆向きなら裏返す。
- 列車の `tags` は、その列車が受け持つ運用で走るタグを、運用の順に1回ずつ並べたものである。タグのない駅間は空の文字列で表す。運用に入っていない列車は書かない。

路線を選んだ地図は、タグで別の道を走る列車の線路も出す。路線の駅をつなぐタグなしの区間の線路に加えて、その路線の列車の駅間ごとに、その駅間のタグ(`tagAt`)の区間の線路を足す。ワールドにないタグは、一覧にないタグの区間(`otherTag`)を使う。Java の `MapSelection` と JavaScript の `visible` は、共通のテスト用ケース `map/cases/tags.json` で、同じ線路を出すことを確かめている。

表示するタグは、「タグなし」とワールドのタグを、それぞれオンかオフにして選ぶ。初めはすべてオンで、オフにしたものだけを覚える。そのため、あとで作ったタグはオンで出る。決まりは次のとおりで、Java の `TagView` と JavaScript の `tagSegments` が、共通のテスト用ケース `map/tagviews/*.json` で同じ結果になることを確かめている。

- 線路を、タグの区間の境目で分ける。タグのある部分は、そのタグのどれかがオンなら出し、オンのタグの色で描く。オンのタグが複数あれば、その色を交互に描く。
- タグのない部分は、「タグなし」がオンなら出す。オフなら、出ているタグの部分どうしをつなぐところだけを出す。タグのない線路のひとまとまり(タグのある部分で区切られたもの)のうち、出ている部分に2か所以上で接するものである。行き止まりの側線や、オフのタグの区間にしかつながらない枝は出さない。まとまりの先端から、ほかとつながらない部分を順に外してから数える。出ている部分に接する点では、まとまりどうしをつながない。そこから出て、ループ線で折り返して戻るだけの線路は、出ている部分に1か所でしか接しないので出さない。線路の端どうしは、線路の名前(`key`)の両端の位置が同じならつながっているとみなす。
- 出ない部分は消さずに、目立たない薄い灰色で描き、タグの色を使わない。路線の選択から外れた線路も同じである。出る線路は、路線の選択とタグの選択の両方を満たすものである。
- 駅、信号、制限速度標識は、出ている部分の上にあるときだけ描く。線路の上の位置は、点の並びの長さの割合で求める。
- 列車は、運用で走るタグのどれかがオンのときだけ描く。タグのない駅間を走る列車と、運用に入っていない列車は、「タグなし」として扱う。描くのは、出ている部分の上にある車両だけである。

### 地図の画面

ワールドに置くブロック「地図の画面」(`map_screen`)は、同じ地図を壁に映す。

- 置くと、置いた人のほうを向く。同じ向きで、壁の中で隣り合うブロックは、ひとまとまりになる(`ScreenGroup`)。ひとまとまりが長方形を埋めていて、縦横とも設定 `map_screen_max_size`(既定32、1〜64)以下なら、全体で1枚の画面になる。上限を64にしたのは、画面の各ブロックが、地図が変わるたびに線路全体から自分の分を組み直し、サーバーもブロックを置き換えるたびに並びを探すからである。サーバーが探すのは上限の2乗より1つ多いブロックまでで、それより大きい壁の一部を1枚の画面と取り違えない。そうでなければ、1ブロックずつの画面になる。作っている途中や、1つ壊したあとでも、何かを映すためである。探すのを途中でやめた大きすぎるまとまりでは、見つけたブロックが前に入っていた画面のブロックも全部、1ブロックずつの画面にする。見つからなかったブロックに、前の画面の位置が残らないようにするためである。
- 映すものの設定は、画面のどのブロックも同じものを持つ。親のブロックを決めないので、どのブロックも自分の受け持ちだけを描ける。ひとまとまりが変わったときは、最後に設定したもの(同時なら左下のブロックのもの)を全体に配る。新しく足したブロックは、まだ設定していないので、画面の設定を受け継ぐ。
- 設定は、中心の X と Z、画面1ブロックが映すワールドのブロック数(0.25〜4096)、映す路線、出すものの種類(駅、駅名、信号、信号の柱と灯、制限速度、列車)、オフにした線路のタグ(「線路の地図」の節の「表示するタグ」と同じ決まり)である。タグは設定の画面の路線の下に、「タグなし」を先頭にしてタグの色で並べる。路線とタグは、ボタンの上に入る分だけ並べ、入りきらない分は前の選択を保つ。出すものの種類は、1列で入らない高さ(GUI を大きくしたときなど)では2列にする。ブロックを使うと設定の画面が開き、変えられるのは、そのブロックから8ブロック以内にいて、そこで建築できる人だけである。アドベンチャーモードの人と、スポーン保護の範囲で建築できない人は、設定の画面を開けない。路線は、運行中のダイヤの路線から選ぶ。ダイヤの路線の名前には長さの上限がないが、設定の画面に送れるのは256文字までである。それより長い名前は256文字に収まるように切り、最後に「…」を付けて送る。長いまま送ろうとすると、Minecraft が文字数の上限を超えたとして例外を出す。中心の X と Z は、ワールドの境界をいちばん広げたときの範囲(±3,000万ブロック)までにする。超える値を打つと、その欄の文字を赤くして「完了」を押せなくし、ボタンのツールチップに理由を出す。前は、サーバーが何も知らせずにその設定を捨てていたので、「完了」を押しても何も起きないように見えた。
- 設定の画面の「線路全体を入れる」は、いまチェックしている路線とタグで出る線路(灰色の線路を除く)が収まる中心と縮尺を入れる。出る線路が1本もなければ、その次元の線路全体にする。出る線路はサーバーにしか分からないので、設定の画面を開いているあいだ、チェックしている組をサーバーに尋ね、答えが届くまでボタンを押せなくする。答えのない組は、2秒を待たず、前の頼みから12 tick たったら尋ねる(サーバーは1人に10 tick に1回しか答えない)。
- 設定の画面の「地図で選ぶ」は、映す範囲を地図の上で選ぶ画面を開く。ウィンドウ全体に地図を描き、真ん中に画面の枠を置いて、枠の下で地図を動かす。枠の中は画面のブロックと同じように描き、枠の外は線路だけを暗くして描く。描く処理はブロックと同じ `MapPainter` を使う。枠の中のものは画面のブロックと同じ順に重ねる。駅名は列車の下に、標識の数字は駅と信号の下になる。画面の1ブロックを描く大きさは、ウィンドウに入る大きさから、枠の縦と横がどちらも整数の画素になるところまで小さくする(`AreaPick.block`)。そうしないと、枠の線と、枠の中に描いたものの端が1画素ずれる。ドラッグで地図を動かし、ホイールでカーソルの下の場所を保ったまま拡大と縮小をする。開いたときの範囲は点線の枠で残し、どれだけ動かしたかが数字を読まなくても分かるようにする。色を地図のもの(タグ、信号の灯、列車)だけに使うため、枠と文字は白と灰色だけで描く。「完了」で中心と縮尺を設定の画面の欄に入れ、「キャンセル」と Esc では何も変えない。
- 設定の欄に入る数が切りのよいものになるように、地図で選ぶ中心は動かすたびに整数のブロックにそろえ、縮尺はホイールを3ノッチ回すごとに隣の刻みに移す。途中で逆に回すと、そこから数え直す。ドラッグを始めたときも数え直す。刻みは 0.25、0.5、0.75、1、1.5、2、3、4、6、8、12、16 … 4096 である(`MapProjection.STEPS`。1から上は2のべき乗と、その1.5倍)。欄に打った 20 のような刻みにない値からは、16 か 24 に移る。1より下を4分の1ずつにしたのは、欄に書く数が小数第2位までだからである。欄の数は末尾の0を書かず、1.50 は 1.5 と書く。刻みの間の値に合わせたいときは Shift を押す。押しているあいだはそろえず、ホイールは運行図と同じ速さで拡大と縮小をする。中心は、サーバーが受け付ける ±3,000万の外へは動かさない(`ScreenSettings.MAX_CENTRE`)。
- 各ブロックは、`MapProjection` が決める受け持ちの範囲を、北を上にして描く。線路は範囲で切り取る(`MapProjection.clip`)。大きさは画面のブロックを単位にするので、映す範囲が広くても狭くても、線や印の太さは変わらない。駅、信号、標識の印と文字は、画面の短い辺の平方根に比例して大きくする(1×1 で1倍、4×4 で2倍、16×16 で4倍)。大きい画面は離れて見るので、ブロック単位で同じ大きさでは小さく見えるからである。線路と列車の太さは変えない。
- 印の形は次のとおりにする。変えるのは画面のブロックだけで、書き出しと編集ページは変えない。
  - 駅: 列車が入って止まる向きを指す五角形。向きは、駅の点の場所の最初の節点から2つ目の節点へ向かう向きで、Create が駅に入れる向き(`GlobalStation.canApproachFrom`)である。
  - 信号: 線路の上に、列車を止める向きを指す小さな三角を、最初の灯の色で描く(駅の五角形と見分けるため)。信号のブロックがある側に柱を出し、その先に黒い箱を描いて、灯を進む向きに並べる。箱はいつも2灯分で、点いていない灯は暗い灰色にする。1灯の信号と2灯の現示で見た目が変わらないようにするためである。両側に頭のある信号は、向きごとに描く。設定で「信号の柱と灯」を外すと、柱と箱を描かず、線路の上の三角だけにする(画面のブロックだけの項目で、編集ページの地図にはない)。
  - 制限速度標識: 標識は片方の向きの列車にしか効かないので、線路の上に、効く列車の進む向きを指す「>」の形の線の矢印を描く(制限は赤、解除は白で縁どった黒)。塗りつぶした三角にすると、赤い標識が止まれの信号に見えたので、形で見分ける。標識のブロックがある側に柱を出し、その先に、数字が入るだけの幅の、赤で縁どった小さな板を描く。解除標識は、Create Train Next のブロックの絵と同じく、黒で縁どった白い板に、上下から黒い三角が中央で接する形にする。
- 印どうしが重ならないように、画面全体の印をまとめて置く(`MarkLayout`)。線路(出る線路も灰色の線路も)と、駅と、線路の上の信号の印は動かさず、当たり判定にする。そのあと、信号の頭、標識、駅名の順に、候補の位置から、先に置いたものと重ならない最初の位置を選ぶ。当たり判定は傾いた箱どうしで行い、斜めの線路や、斜めの線路に沿った信号の頭も、そのままの向きで比べる。信号の頭と標識は、ブロックのある側(サーバーが、ブロックの位置が列車の進む向きの左右どちらかを送る)で、柱を伸ばして線路から離し、線路に沿って前後にもずらしてみて、どれもだめなら反対側を試す。左側通行の線路でも、ワールドの配置どおりの側に出るようにするためである。柱も当たり判定に入れ、柱がほかの線路や印をまたぐ位置は選ばない。前後にずらさずに反対側へ逃がしていたときは、隣の信号の頭に場所を取られた頭が、隣の線路をまたいで反対側に出た。駅名は、駅の印の真ん中の右上、右下、左上、左下、上、下を試す。どこも重なるときは、信号と標識は最初の位置に重ねて描き、駅名は描かない。印は、画面全体の配置を一度求めて覚えておき(線路網、答え、設定、画面の大きさ、サーバーから届いた信号などが変わったときだけ求め直す)、各ブロックは、印の位置が自分の範囲にあるものを描く。
- 線路と駅は、クライアントが Create から受け取っている線路グラフを、編集ページの地図と同じ部品(`CreateMap`)で読む。線路が変わってから1秒たったら読み直す。線路の形はサーバーから送らない。
- サーバーにしか分からないものは、画面が描かれているあいだだけ、クライアントが尋ねる。サーバーは、だれが画面を見ているかを覚えない。
  - 選んだ路線が映す線路の鍵と、オフにしたタグでの線路の区間: 2秒ごとに、見えている画面の設定(路線とオフのタグの組)をすべて1つの頼みにまとめて尋ね(16組まで。答えのまだない組から)、線路網、タグの一覧、ダイヤが変わって答えが変わったときだけ送る。路線を選ばなければ、隠す線路の鍵だけを送る。区間は、全体がタグなしで出る線路を除き、出る区間とそのオンのタグ、出ない区間を送る。タグの区間は、サーバーにしかない区間の情報から求めるためである。タグの色はタグの一覧からクライアントが引く。
  - 頼みを組ごとに別々に送っていたときは、サーバーが1人に10 tick に1回しか答えないので、設定の違う画面が2つ以上あると、最初の組にしか答えが返らなかった。答えのない画面は、全部の線路をタグなしで描くので、タグをオフにしても線路が白いまま残った。
  - 画面は、出る区間をオンのタグの色で描き、複数のタグは短い長さごとに色を替える。タグのない区間は明るい灰色で描く。路線の選択でもタグの選択でも外れた線路は、消さずに暗い灰色で描き、その上の駅、信号、標識、列車は描かない。
  - 信号の表示、列車の位置、制限速度標識: 0.5秒ごとに、その人のいる次元の分を送る。列車には、運用で走るタグも付けて送り、画面はオフのタグだけで走る列車を描かない。信号の頭がどちら向きにあるかと、いま何を示しているかは、Create がクライアントに送っていないためである。標識の上限は、Create Train Next が置いたときにしかクライアントの線路グラフに送らず、変えた値は送らないため(ワールドを読み直すまで古い値が残る)、信号と一緒に送る。
- 線路は、折れ目の外側の縁を延ばしてつなぐ(マイター)折れ線として描き、端は点で直角に切る(`Polyline`)。線分ごとに半幅ずつ延ばして描いていたときは、曲線の折れ目に角が出て、縞の隣どうしが重なって色がはみ出した。線路どうしは、Create が節点で同じ向きに通すので、端を延ばさなくてもすき間なくつながる。とても鋭い折れ目は、半幅の4倍で切る。駅名や標識の数字は、乗せる物のすぐ上の層に描き、層の間も0.0005ブロックに縮めて、斜めから見ても浮いて見えないようにした。
- 運行図と同じく、1人に答えるのは決まった間隔に1回までにする(`RequestLimit`)。

### 運行は、ダイヤのとおりに列車を直接動かす

目指すのは、1日のダイヤグラムを手で作れば、列車がそのとおりに動くことである。ダイヤグラムを作る画面(M6、M7)はまだないが、どちらもダイヤの JSON を受け渡しに使う。そこで運行は、その JSON だけを元にして動く。Create の時刻表(`Schedule`、`ScheduleRuntime`、待機条件)は使わない。Create から借りるのは、線路と列車と走行(`Navigation.startNavigation`)だけである。経路は、Create の探索(`Navigation.findPathTo`)を写した自前の探索で決める(4.)。

現実の鉄道では、1日の運行を「運用」にまとめ、英数字の番号(例: 12A)で呼ぶ。どの編成がどの運用に入るかは決まっておらず、車庫から出る順に入る。運行は次のように動く。

1. `/rttimetable load`(権限レベル2。名前は仮)で、ワールドの `createrealtimeschedule/timetable.json` を読む。誤りがあれば、チャットに最初の10件を出して断り、それまでのダイヤを続ける。なければ、そのダイヤで運行を始める。ダイヤは読んだ JSON のまま SavedData に保存する。`/rttimetable status` は運用ごとの位置と遅れを、`/rttimetable unload` は運行の停止を受け持つ。
2. 運用は、車庫を出てから戻るまでの停車の列になる。前の列車の終着と次の列車の始発は、同じ駅での1回の停車にまとめる。回送もダイヤの列車なので、車庫を出る時刻も戻る時刻もダイヤが決める。
3. 運用の最初の発車の `duty_lead_seconds`(既定60秒)前に、車庫の駅で空いている列車のうち、空いてからいちばん長く待っている1本を、その運用に入れる。空いた列車とは、車庫の名前の駅に止まっていて、行き先がなく、Create の時刻表を持たず、運用に入っていない列車である。同時に入れる運用が複数あれば、発車の早い運用から選ぶ。
4. 発車の時刻になったら、列車を次の停車駅へ送り出す。送り方は Create の行き先の命令と同じで、その名前の駅すべてのうち、いちばん良い経路のものを選ぶ。経路は自前の探索(`CreateRoutes`、`RouteSearch`)で見つけ、Create の `DiscoveredPath` にして `startNavigation` に渡す。探索は Create の `Navigation.search` と同じ重みで道を比べる。通る駅ごとに50、ほかの列車がいる駅に300、レッドストーンで赤にした信号に400、列車のいる信号区間に25から(1つごとに半分)、ほかの列車の先頭と最後尾がいる辺にその列車の重み(この MOD の列車は350)を足す。台車が走れない種類の線路は通らない。前と後ろの運転台に合わせて両方向を探し、Create と同じ規則でどちらかを選ぶ。探す順も Create に合わせた。長さと重みに、Create と同じ式で見積もった残りの道のり(A*。ノードの位置から出す)を足した値の順に調べ、分岐の枝は線路グラフの順に見て、同じ値の道どうしは Create の待ち行列と同じ順で取り出す。そのため、同じ名前のホームが複数あるときも、Create と同じホームを選ぶ。線路グラフの読み取りは、指紋が変わるまで使い回す。指紋は1秒に1回まで取り、線路の種類、辺の置き直し、点が列車を通すかどうか(組み立て中の駅など)も入れる。その1秒のうちに列車の下や道の辺が変わっていれば、すぐ読み直して探し直す。経路探索を自前にしたのは、線路のタグ(M10)で、列車ごとに通れる線路を変えるためである。所要時間の見積もりも同じ探索の道で求めるので、見積もった道と走る道が同じになる。ほかの列車がいるホームは避けられる。ダイヤが線路のタグを指定した駅間では、そのタグの列車が走れる線路だけを通る道を探す(「線路のタグ(M10)」の節)。道がなければ発車せず、毎 tick 探し直してログに出す。列車が駅を離れるのも走るのも Create である。着いたら、到着の時刻から発車の時刻を決める。
5. 発車は、第1段階の待機条件と同じ規則 `D = max(T, A + M)` で決める。T はダイヤの発車、A は実際の到着、M は最短停車時間である。M は、ダイヤの停車の値、なければ駅の値、それもなければ設定 `default_minimum_stop_seconds` を使う。早く着けば時刻まで待ち、遅れて着けば最短停車だけして出る。車庫での最初の発車に、最短停車はない。
6. 実際の到着と発車の時刻を、運用ごとに記録する。M6 の運行図で、計画の線に実績の線を重ねるためである。発車は、列車を送り出した時刻ではなく、列車が実際にホームを離れた時刻で記録する。Create は、送り出された列車を次の tick に動かし、先の信号が赤ならホームで待たせるからである。信号で待っているあいだも、遅れはその分だけ増えていく。
7. 最後の停車(車庫)に着いた列車は、空きに戻る。

ダイヤは1日分で、毎日くり返す。営業日 d の運用は、d の0時に最初の発車の時刻を足した時に始まる。`24:30` のように24時を過ぎた時刻は、翌日の0時30分である。同じ営業日に、同じ運用は1回しか入れない。

うまくいかない場合は、次のように扱う。

- 最初の発車までに空いた列車がなくても、すぐには運休にしない。ダイヤに戻れる見込みがあるあいだは空いた列車を待ち、遅れて出す(次の節)。見込みがなくなれば、その日のその運用は運休にし、ログと `/rttimetable status` に出す。サーバーが止まっていて最初の発車を過ぎた運用も、同じに扱う。何日も止まっていても、運休は1回だけ記録する。ダイヤを読み込んだ時点ですでに始まっているはずの運用も、遅れて出す。戻れる見込みがなければ、運休として数えず、翌日から走らせる。
- 走っている列車がなくなった場合、脱線した場合、プレイヤーが Create の時刻表を入れた場合は、その運用を中断として記録し、その列車には手を出さない。
- 次の駅への経路がなければ、毎 tick 送り直し、ログに1回だけ出す。
- `/rttimetable load` で読み直したときは、走っている運用は、新しいダイヤにも同じ停車の列があれば続け、なければ中断する。`unload` では走っている運用を中断し、列車は向かっている駅に着いて止まる。

Create の時刻表を持つ列車と、車庫に止まっていない列車には触れないので、同じ線路で、ダイヤの運用と Create の時刻表で走る列車を混ぜられる。

初めは、運用を Create の時刻表に変換し、行き先の命令と `real_time_of_day` の条件を並べて列車に入れる案だった。ダイヤを唯一の元にするため、Create の時刻表に依存しない別の機能に改めた(2026年10月)。変換した時刻表を経ると、その時刻表とダイヤの二つが運行を決めることになる。その代わり、Create の案内板や Display Link には、列車番号や行き先が出ない。出す方法は、あとで考える。第1段階の待機条件 `real_time_of_day` は、Create の時刻表を手で書く人のために残す。

### 大きな遅れは、運休でダイヤに戻す(M8)

発車の規則 `D = max(T, A + M)` で詰められる遅れは、停車の余裕(停車時間から最短停車時間を引いた分)と、走りの余裕(ダイヤの所要時間から線路の所要時間を引いた分。列車はいつも全速で走る)までである。それを超える遅れは、車庫に戻るまで残る。そこで、遅れが基準を超えた列車は、ダイヤの列車を運休してダイヤに戻すことにした。鉄道の運転整理でいう間引きにあたる。ダイヤにない列車は走らせず、することは、列車を駅で待たせることと、そのあいだの列車の運休だけである。基準は設定 `recovery_threshold_seconds`(既定600秒)で、0 にすると、この節のことは何もしない。

列車が停車 i の駅 Q に着いたとき、次のように決める。

1. 決まった発車の遅れが基準以下なら、何もしない。
2. 候補は、同じ運用でこのあと Q を出る停車である。早い順に見る。
3. 最初の候補まで全部走ったときの遅れを見込み、基準以下に戻るなら、何もしない。見込みでは、各区間を線路の所要時間で走り、各駅に、最短停車時間だけ、ダイヤの時刻までは止まる。区間の所要時間は、運行図の縦軸と同じく、最初に要るときに線路から求める。線路にない区間は、ダイヤの所要時間で数える。信号は定刻のダイヤの列車を信号とともに走らせた再現(「Create Train Next の制限速度標識を、所要時間に含める」の節)で、その区間が延びた分を足す。遅れた列車が信号で止められる分は、定刻のときと同じとみなし、ダイヤにない列車は入れない。
4. そうでなければ、候補を順に見て、次をすべて満たす最初の停車 c を選ぶ。
   - Q で待って c から出たときの遅れが、基準以下である。出る時刻は、c の時刻、着いてから最短停車時間が過ぎた時刻、今のうちで、いちばん遅いものである。
   - 運休になる列車に、ダイヤで運休しない印(`"keep": true`)を付けた列車がない。あれば、それより後の候補も見ない。
   - c のあとに、客を乗せる列車が残っている。回送で車庫に帰るだけになるなら、運用の仕事をすべて運休することになるので、待たせない。
   - 待つあいだ、ほかの列車の邪魔にならない。ダイヤの列車が Q を止まらずに通ることがない。また、いま Q にいる列車と、これから Q に止まりに来る列車に、この列車を足しても、Q の名前の駅(この列車の線路網にあるもの)の数を超えない。これから Q に着く列車(遅れての出庫)では、いま Q にいる列車は数えず、着いてから出るまでにダイヤで Q に止まっている列車を数える。いまいる列車は、着くころには出ているかもしれないからである。線路のタグ(M10)を指定した駅間で Q に着く列車は、そのタグに開いたホームにしか止まれない。そこで、そのホームの数と比べ、いまそのホームにいる列車と、そのホームに止まりうる列車だけを数える。止まりうる列車とは、Q に着く駅間のタグに開いたホームが、この列車のものと重なる列車である。タグのない列車と、車庫を出る列車は、どのホームにも止まれるものとして数える。Q を止まらずに通る列車でも、通る駅間のタグに開いたホームがこの列車のものと重ならなければ、邪魔にならないものとする。
   - 今いる所から c の次の駅へ、Create の経路探索で道が見つかり、ダイヤの所要時間に基準を足した時間のうちに着ける。後ろへ走れない列車が折り返す候補は、ここで外れる。経路探索は道を探すだけで、列車は動かさない(Create 6.0.10 のソースで確かめた)。
5. 選べたら、列車は Q で待ち、c の停車から出る。あいだの停車は飛ばし、そこを走るはずだった列車は運休になる(一部だけ飛ばす列車は、途中まで走る)。選べなければ、遅れたまま走る。

例として、30分で A と B を往復する運用を考える。1往復の余裕は2分、基準は10分とする。12分遅れて A に着いた列車は、次に A を出るときには遅れが10分以下に戻るので、そのまま走る。25分遅れなら、次の往復でも20分ほど遅れるので、1往復(2本)を運休し、A で待って、その次の往復から定刻で出る。

一度決めた運休は取り消さない。判断は列車が駅に着くたびにする(遅れての出庫を待つ運用は、毎秒見直す)ので、見込みより遅れれば、次に着いた駅でまた決める。決めたことは、理由と運休した列車をつけて、ログと `/rttimetable status` の注意に出す。組み合わせを探す最適化はしない。決まった規則のほうが、結果を説明しやすく、テストで確かめやすいからである。

最初の発車までに空いた列車がない運用も、すぐには運休にしない。今車庫を出たとして、次のどれかにあたるあいだは、空いた列車を待つ。

- 車庫の次の駅を、基準以内の遅れで出られる。
- その先で、基準以内まで取り戻せる。
- その駅で待てば、あとの停車から基準以内の遅れで出られる(上の規則のとおり、そのあとに客を乗せる列車が残っていること)。

列車が空いたら遅れて出し、車庫の次の駅に着いたときに、上の規則で待たせるかを決める。待てるのは、次の日の同じ運用が始まる lead の1 tick 前までで、そこで運休にする。空いた列車の取り合いでは、遅れていない運用を先にする。ダイヤを読み込んだ時点ですでに始まっているはずの運用も、同じように遅れて出す。戻れる見込みがなければ、これまでどおり、運休として数えずに翌日から走らせる。

運行図では、運休した列車の計画の線を薄く描く。待たせた列車の実績の線は、着いてから出るまで、その駅に止まっている1本の線になる。

まだしていないことは、運用の差し替え(折り返し駅で、遅れた列車と、そこに止まっている列車とで、残りの運用を入れ替える)、見込みを運行図に出すこと、遅れた列車がほかの列車と信号で止め合う分を見込みに入れること(信号は、定刻のときの分だけ入れている)である。

### 待避は三つの段階で実現できる

各駅停車が待避駅で快速の通過を待つ動きには、三つの作り方がある。

1. 時刻で待避する。各駅停車の出発時刻を、快速が通過したあとに設定する。M2 の時点でもう組める。快速が遅れると崩れる。
2. Create の部品で待避する。列車観測ブロックと、レッドストーンリンクの待機条件を組み合わせる。今の Create でも組める。
3. ソフトウェアの条件で待避する。「列車 X が地点 P を通過するまで待つ」という条件を足す。列車が観測ブロックに先頭で入ると `occupiedObservers` に加わり、最後尾が抜けると外れる。これで通過を検出できる。観測ブロックを置かずに駅を検出するには、列車の位置を自前で見張る必要がある。Create は、駅を通過するだけの列車をイベントにしていないためで、試作が要る。

待避線の配線は、Create の信号と経路探索に任せる。各駅停車が待避線の番線に入り、快速が本線を通る構成では、番線の名前で行き先を分ければ、経路探索が振り分ける。信号は先に区間を確保した列車を通すので、待避の指示がないと、各駅停車が先に分岐へ出て快速を止めることがある。

### 待避と緩急接続(M9)

M9 では、3 をダイヤの停車の条件として作った(形式は第5版の `wait_for`)。停車に「列車 X が駅 P を出る(止まらずに通る)まで待つ」を持たせ、快速の通過を待つ待避と、快速が止まって先に出る緩急接続の両方を、これで表す。P は指定できる。本線と待避線で番線の名前が分かれるからで、省けば自分の停車の駅になる。各駅停車は、発車の時刻が来ても、X が P を出る(通る)までは出ない。待つのは、ダイヤで X が P を出る(通る)ときのうち、この停車の発車より前の最後のものである。

- その日の X の運用が走っていないなら、待たない。運休、まだ始まっていない、もう終わった、中断した、のどれでもそうである。X の運用が待たせられて、その停車や区間を飛ばしたときも、待たない。その停車で待たせられて、後の停車から出るときも、X は運休なので待たない。
- 待つ相手が決まらない待ちは、待たない。X がどの運用にも入っていないときと、線路で決まる X の道筋では、それより前に P を出ることも通ることもないとき(環状線で反対に回るとき)である。ダイヤの検証は線路を知らないので、これは、ダイヤを読み込んだときと `/rttimetable status` で知らせ、サーバーのログにも書く。
- ダイヤは、定刻なら待たずに済むように組む。X が P を出る(通る)のは、ダイヤの上では、各駅停車の発車より前にしておく。待ちが各駅停車を時刻より後まで止めるのは、X が遅れたときだけである。
- X が P に止まるなら、X が P を出た(ホームを離れた)あと、ダイヤでの X の発車から各駅停車の発車までの間を空けて、待ちが終わる。X が d 秒遅れて出れば、各駅停車も d 秒遅れて出る。間は、X が出た秒の頭から数える。ダイヤの時刻は秒単位で、時刻どおりに送り出した列車は、その次の tick にホームを離れるからである。こうして、X が時刻どおりに出れば、各駅停車も時刻どおりに出る。
- X が P を通るなら、X の最後の車両の後ろの端が、名前が P の駅を過ぎたときに終わる。環状線でどちら回りに P を通るかは、運行図の軸と同じく線路から決める。Create は、行き先でない駅を通る列車に何も知らせないので、X の後ろの端の位置を毎 tick 写しておき、次の tick にその位置から列車が動いた分だけ走らせ直して、過ぎた駅を見る。X が通ったら、各駅停車はすぐに出てよい。その先で X との間を保つのは、Create の信号である。ただし、X がとても遅く P を通ると、X の先頭がまだ合流の手前の信号に届かず、合流の区間を取っていないことがある。そのときは、先に出た各駅停車が合流の区間を取り、X がその後ろで止められる(ゲームテストで起きた。下の段落)。Create が列車の点を動かすのと同じやり方なので、1 tick に短い辺をまたいでも見落とさない。見張り始めの tick(再起動のあとなど)は、写しがないので、今の位置から動いた分だけ戻した所を写しとする。後ろの端は、先頭が次の停車に着いても P の手前にいることがあるので、その一つ前の区間も見張る。通ったことは、X の運行に記録して保存する。
- X が P を通ったと見えないまま、次の次の停車に着いたときも、待ちを終える。X の道に P の名前の駅がない(本線に駅を置いていない)ということで、注意に出す。次の停車で終えないのは、長い列車では、先頭がそこに着いても、後ろの端がまだ P の手前にいることがあるからである。
- 待ち合わせの限度: 待つのは、自分の発車の時刻から、停車の `max_wait`、なければサーバーの設定 `max_wait_seconds`(既定300秒)までである。それを過ぎるか、X が出る(通る)見込みがそれより遅ければ、待たずに出て、注意に出す。見込みは M8 の予測で、止まる場合は、P を出る見込みにダイヤでの間を足したもの、通る場合は、P の手前の停車を出る見込みにする(いちばん早い場合)。限度があるので、配線の都合で X が各駅停車の後ろでつかえるときも、待ち続けない。
- 待っている列車は、`/rttimetable status` に、どの列車を待っているかを出す。

ゲームテストのダイヤは、定刻なら待たずに済む組み方にしてある。待ちを起こすときは、テストが快速のスロットルを 0.05 に下げて遅らせ(秒速約1.4ブロック)、12:02:40 に戻す。線路は、現実の待避に多い複線の片側の形にした。各駅停車と快速が同じ線路を走り、A で各駅停車が待避線に入る。本線の南に待避線を並べ、両端をS字の曲線で本線につないだ(どちらの端も本線の途中から分かれる分岐になる)。信号は、分岐の手前、待避線の入口と出口、合流の手前、合流の先に置き、分岐の区間、待避線のホーム、合流の区間を分けた。各駅停車は車庫を 12:02:00 に出て、分岐から待避線に入り、A2 に 12:02:07 に着く。A2 を出る予定は 12:02:35 で、後ろの車庫を 12:02:15 に出る快速は、定刻ならその前に本線の A を通る(または出る)。確かめたのは次のとおりである(Create 6.0.10-281)。

- 快速が A を通る、定刻: 快速は 12:02:26 に B に着き、各駅停車は時刻どおり 12:02:35 に出た。
- 快速が A を通る、遅れ: 快速は 12:02:44 ごろに A を通り、各駅停車はそれまで待って出た。快速は待避線の各駅停車に止められずに本線を通り、12:02:48 に B に着いた。各駅停車は合流の区間が空くのを信号で待って本線に戻った。
- 快速が A に 12:02:23 から 12:02:27 まで止まる(各駅停車との間は8秒)、定刻: 快速は 12:02:27 に、各駅停車は 12:02:35 に、どちらも時刻どおりに出た。
- 快速が A に止まる、遅れ: 快速は 12:02:45 に着いて 12:02:47 に出て、各駅停車は8秒後の 12:02:55 に出た。
- 最長の待ち時間が0秒で、快速が遅れ: 各駅停車は時刻どおりに出て、待たなかったことが注意に出た。

待ちの処理を止めると、遅れの3件が落ちる。待つ相手の運用が走らないときに待たないことは、周回線で確かめた。テストは見て確かめられるよう、終わったあとも5秒走らせる。直線なので、列車は車庫に戻らない。

初めは、待避線のテストで、快速を A を過ぎるまで遅いままにしていた。すると、各駅停車が合流の区間を先に取り、快速は合流の手前の信号で止められた(上の箇条の、とても遅く通る場合)。遅れた列車も、ふつうは線路の速さで走るので、テストでは A の手前で速さを戻した。

### 線路のタグ(M10)

M10 の前は、本線と待避線のホームを分けるのに、駅の名前を別にしていた(待避線のテストでは A と A2)。M10 では、線路の区間に「タグ」を付け、駅間ごとに列車が走るタグを決められるようにした。待避線のテストも、両方のホームを A の名前にして、タグで分けた形に直した。三つに分けて進めた。

1. 自前の経路探索。Create の探索には、道の選び方を外から変える方法がない。そこで、Create の探索を写した自前の探索で道を決め、Create にはその道を渡して走らせる(「ネットワークの書き出し」と「運行は、ダイヤのとおりに列車を直接動かす」の節)。作った。
2. タグのブロックと区間。作った(この節の残り)。
3. ダイヤ第7版で、駅間ごとにタグを指定する。分岐ではタグの付いた枝を選び、行き先に着けなければ「道がない」として発車しない。この場面はゲームと編集ページで前もって調べ、注意として知らせる。作った(この節の終わり)。

タグはブロックで付ける。ブロックは駅と同じく、先にアイテムを線路に使って、指す位置と向きを決めてから置く。ブロックには両方向と一方向の2種類がある。区間はブロックの向きに、同じ種類で同じ向きの次のブロックまで、または線路の終わりまで伸びる。両方向のブロックのタグは、区間をどちら向きに走る列車にも効く。一方向のブロックのタグは、ブロックの向きに走る列車にだけ効き、逆向きの列車にはタグがないのと同じになる。一方向のブロックを使えば、単線で上りと下りに別のタグを付けられる。1つのブロックはタグを複数持てる。区間が重なった所の線路は、重なった区間のタグをすべて持つ。三つ目では、そのどれかのタグを指定した列車が、そこを走れるようにする。タグが「なし」のブロックは、手前のブロックの区間を終わらせるだけで、区間を作らない。逆向きのブロックと、種類の違うブロックでは、区間は終わらない。

区間の誤りは二つある。一つは区間が終わりより手前で分岐に着くことで、区間がどちらの枝へ続くか決まらない。分岐とは、進む向きに線路が二つ以上に分かれる節点である。合流では進む先が一つなので、誤りにしない。もう一つは両方向と一方向のブロックを混ぜることで、区間が種類の違うブロックの区間と重なるか、種類の違うブロックが区間の中にあると誤りにする。1つの区間は、どちらかの種類のブロックだけで作る。誤りはブロックの画面と `/rtnetwork tags` で知らせる。誤りのある区間も辿れたところまではタグを付けたままにする。一つのブロックの誤りで、ほかの線路の扱いを変えないためである。

タグはワールドごとの一覧で、id と名前と色を持つ。色は、地図でそのタグの区間を描く色である。タグの画面で、種別と同じ7色の見本から選ぶか、`#rrggbb` の形で書く。「名前で決まる色」を押すと、決めた色を外す。色を決めていないタグは、種別と同じ規則で名前から色を選ぶ。ブロックは id だけを持つので、名前を変えると、すべてのブロックが新しい名前になる。ダイヤはタグを名前で書くので、名前を変えたら手で直す。タグはブロックの画面から、誰でも作る、名前を変える、消すことができる。名前には、改行などの制御文字は使えない。ダイヤに書けないためである。サーバーは、プレイヤーがブロックから64ブロック以内にいることを確かめ、離れていればそう知らせる。消せるのは、線路上のどのブロックにも付いていないタグだけである。id は二度と使わない。線路が取り外されて、線路を指していないブロックは、タグを使っているブロックの数に入らない。そのあいだにタグが消されたら、そのブロックは次に読み込まれたときにタグなしになる。

作りは Create の駅や列車観測ブロックと同じである。ブロックは Create の線路グラフに自分の種類の点(`createrealtimeschedule:track_tag`。共通の初期化で、サーバーとクライアントの両方に登録する)を置き、点がタグとブロックの種類を持つ。2種類のブロックは、同じ種類の点とブロックエンティティを使う。アイテムで置く場所を選ぶあいだ、Create は信号機と列車観測ブロック以外の点に駅の印を出し、それを変える入口がない。そこで、Create が選んだ場所をリフレクションで読み、Create の印を出さずに、タグのブロックの印を出す。点は駅と同じく、後ろの節点から、ブロックが向く節点への辺の上に置かれる。区間を辿る `TagSections` は、Minecraft にも Create にも依存しない部品で、`CreateNetwork` が読んだ点の上で動く。線路グラフの指紋にはタグも入るので、タグを変えると、運行の探索は線路を読み直す。

三つ目では、ダイヤ第7版の `tag` で、列車ごと、駅間ごとに走るタグを決める(「ダイヤの JSON 形式」の節)。タグを指定した列車の道は、次の規則で選ぶ。線路の各点はそこを覆う区間のタグをすべて持つ。指定したタグを持たない区間だけに覆われた所には入らず、その手前の駅には止まれる。区間のない線路は走れる。出発するときに列車がいる区間は、タグが違っても、その区間の終わりまで走ってよい。違うタグのホームに止まっている列車も、そこから出られるようにするためである。分岐では、次の分岐までに指定したタグの区間がある枝があれば、その枝だけを選ぶ。ただし、その区間より手前に列車が走れない所(指定したタグを持たない区間、逆向きの信号、列車の台車に合わない種類の線路)がある枝は数えない。ワールドの一覧にない名前のタグを指定した列車は、どの区間にもないタグとして扱うので、区間のない線路だけを走る。タグを指定しない列車は今までどおり Create と同じ道を選ぶ。両方向のブロックの区間は両向きの列車に効き、一方向のブロックの区間はブロックの向きに走る列車にだけ効く。

所要時間は駅名の組とタグごとに求める。タグごとの駅間は、そのタグの列車が止まれるホームから探す。指定したタグを持たない区間だけに覆われたホームからの道は、止まれるホームのどれからも行けない駅への道にだけ使う。運行図の軸はタグなしの駅間で作る。

ゲームはダイヤを読み込んだときと `/rttimetable status` で、タグでは道がない駅間と、ワールドにないタグを知らせ、ログにも出す。同じ名前のホームが複数あると、着いたホームによって次の駅間の道が変わる。そこで、運用ごとに車庫の名前のホームから始め、駅間ごとに着くホームを順に辿る。運用に入っていない列車は、最初の停車の名前のホームすべてから辿る。どのホームからも道がない駅間を「道がない」とする。編集ページは書き出し第3版の `ways` を使って同じ規則で調べ、区間の誤りも注意に出す。Java の `TagWays` と JavaScript の `noWay` が同じ結果になることは、共通のテスト用ケース `operation/ways/*.json` で確かめている。

## 設計の骨格: 公開された入口に部品を足す

時刻表は外から拡張できる。待機条件の一覧(`Schedule.CONDITION_TYPES`)は公開された可変のリストで、ここに条件を足せば、Create の画面と保存の仕組みがそのまま使える。列車の時刻表はサーバーの tick ごとに、オーバーワールドの Level で評価される。時計も同じ tick で進むので、評価の場で `gameTime` を読めば足りる。

部品は次のとおりに分ける。名前は仮である。

- `RealClock`: tick と時刻の変換、日またぎ、周期と枠の計算。Minecraft に依存しない純粋なクラスにして、単体テストで確かめる。
- `RealClockData`: offset を保存する(SavedData)。変更時にクライアントへ送る。
- `SkySync`: サーバー tick の最後に、昼夜の時間を時計から設定する。ゲームルールの元の値も覚えておく。
- `DeparturePlanner`: 出発の規則 D = max(T, A + M) と、枠の選び方(つなげる、数え直す)。これも Minecraft に依存しない。
- `TrainSlotMemory`: 列車ごとの「前の枠」を保存する(SavedData、列車の ID がキー)。
- `TravelTime`、`TrainSpec`、`SpeedZone`(`travel` パッケージ): 駅間の所要時間を、Create の速度制御の再現で求める。Minecraft に依存しない。`TrainSpecs.of(train)` だけが Create を使い、実際の列車(サーバーの設定と、燃料の有無)から `TrainSpec` を作る。カーブの区間は `SpeedZone.curve(…, spec)` で作り、上限は spec の曲がるときの速さになる。
- `Timetable`、`TimetableJson`、`ServiceTime`(`timetable` パッケージ): ダイヤの JSON(路線、列車、運用)を読み書きし、中身を検証する。Minecraft にも Create にも依存しない。
- `RailNetwork`、`Leg`、`NetworkJson`(`railway` パッケージ): 線路網を有向の辺と駅で表し、駅から駅への最短の道(距離、カーブの区間、途中の駅)を探して、所要時間つきで JSON に書く。これも Minecraft にも Create にも依存しない。`CreateNetwork` だけが Create の線路グラフを読み、`RailNetwork` を作る。コマンド `/rtnetwork export` がこれを呼ぶ。
- `JsonOutput`(`json` パッケージ): ダイヤとネットワークの JSON を、いつも同じ配置で書く。
- `DutyPlan`、`DutyRun`、`DutyCalendar`(`operation` パッケージ): 運用を停車の列にし、1日分の進み具合(発車の時刻と実績)を持ち、いつどの列車を入れるかを決める。Minecraft に依存しない。`TrainDriver` は Create の経路探索と走行で列車を次の駅へ送り、`OperationService` は毎 tick に割り当てと運行を進め、`OperationData` はダイヤと運行の状態を保存する(SavedData)。コマンド `/rttimetable` がダイヤを読み込む。
- `RealTimeOfDayCondition`: 待機条件の本体。出発時刻 D の計算と保存、待機中の状態表示、設定画面の1行を受け持つ。
- コマンド `/rtclock` と設定。

設定は次の八つにした。名前と既定値は仮である。ワールドごとに、`serverconfig/createrealtimeschedule-server.toml` に保存する。

| 設定 | 既定値 | 内容 |
| --- | --- | --- |
| `sync_sky` | true | 空を時計に合わせる。false でバニラの昼夜に戻す |
| `start_time` | "06:00" | 保存された時計がないワールドで、時計をこの時刻から始める |
| `align_on_start` | false | サーバーの起動時に、現実の時刻へ合わせる |
| `default_minimum_stop_seconds` | 20 | 時刻表の画面で、新しい条件が最短停車時間として最初に持つ値(0〜600秒)。すでにある条件は自分の値を保つ。ダイヤの運用を走る列車の最短停車時間でもある(ダイヤが駅や停車に値を持つときは、そちらを使う) |
| `duty_lead_seconds` | 60 | ダイヤの運用の最初の発車の何秒前に、車庫の列車を運用に入れるか(0〜3600秒) |
| `max_wait_seconds` | 300 | ダイヤで待つ列車を、自分の発車の時刻から何秒まで待つか(0〜3600秒)。待つ列車がそれより遅れる見込みなら、待たずに出る。ダイヤの待ちが `max_wait` を持てば、そちらを使う |
| `train_length_blocks` | 40 | ダイヤで長さを書いていない列車の長さ(1〜10000ブロック)。列車がふさぐ信号の区間の見積もりに使う |
| `recovery_threshold_seconds` | 600 | ダイヤの運用を走る列車が何秒より遅れたら、列車を運休してダイヤに戻すか(0〜7200秒)。空いた列車がない運用を、どこまで遅れて出すかにも使う。0 にすると、どちらもしない |

## 確認できたことと、まだのこと

| 制限速度標識の読み方 | 直接の依存 / IDで読む | ID で読む(依存なし)。意味は Create Train Next の側で決まった(km/h、片方向、解除標識) |
| Create Train Next を入れたゲームテストの依存の入れ方 | jar を手で置く / ソースからビルドする / CI でもビルドする | jar を `libs/` に手で置いたときだけ、照合のテストを登録する(いまの形)。CI でも照合したくなったら、ワークフローに Create Train Next をビルドする手順を足す |
| 昼夜を変える他の MOD との併用 | 併用不可と明記 / 検出して自動で無効にする | 当面は明記だけ。検出は、要望があれば後で足す |
| 運用で、空いた列車の選び方 | 待ち時間が長い順 / 番線の優先順位 / 手動指定 | 待ち時間が長い順で実装した(M5)。手動指定は、要望があれば足す |
| 運用の列車を、Create の案内板や Display Link に出すか | 列車の名前を列車番号に変える / Display Link に本 MOD の情報源を足す / 出さない | 未定。いまは出ない。運行は Create の時刻表を使わないので、案内板が読むタイトルや行き先が列車にない。M6 では運行図だけを作り、案内板には手を付けなかった |

最初の行は、実際に列車を走らせてみないと決めにくい。周期の短い線を組む人には、便が飛ぶ動きと、遅れたまま出る動きのどちらがよいか、意見をもらいたい。実装では (a) を採り、さらに「つなげた枠が1周期以上離れたら数え直す」という決めごとを足した(待機条件の節)。これは最初の版にはなかった。1周期を超えて遅れた列車が、最短停車のまま走り続けないための決めごとだが、遅れたまま出る動きを望む場合は外せる。

## 実装の段階

第1段階は M1 から M3、第2段階は M4 から M12 である。

| M2 待機条件 | `real_time_of_day`、画面、出発の規則、前の枠の記憶、待機中の表示 | 3駅の周回線で、定刻に出発する。早着で待ち、遅れで停車が詰まる。保存して再起動しても出発時刻が保たれる。`set` で時刻を動かすと、待機中の列車が従う |

M1 は実装した。時計の変換と空の式は Minecraft に依存しないので、単体テストで確かめ、サーバー側の動作はゲームテストで確かめた。ゲームの中で空を見ることと、実際に寝ることは、まだ確かめていない。

M2 も実装した。出発の規則と枠の計算は単体テストで、Create の条件の評価に載せた動作はゲームテストで確かめた。完了の条件のうち、早着で待つこと、遅れで停車が詰まること、`set` に従うこと、保存を経ても出発時刻が保たれることは、線路のない列車で通っている。早着で待つことと、遅れで停車が詰まることは、線路を走る列車でも通っている(一直線の3駅で、周回線ではない)。3駅の周回線を線路の上で走らせることと、設定画面の見た目は、まだ確かめていない。

M3 のうち、実機を要さない分も実装した。最短停車時間の既定値は設定にした。使い方の文書として、`README.md`(英語)と `README.ja.md` を書いた。日本語と英語の翻訳は、条件の分を M2 で済ませてある。ほかに、モッドのテンプレートが残していた例のブロック、アイテム、タブ、設定、起動時のログを取り除き、作者、説明、ホームページをモッドの情報に入れ、`LICENSE`(MIT)を足した。

M3 の完了の条件にある、専用サーバーで複数人が同じ時刻と空を見られることは、実機が要るので、まだ確かめていない。手順は次のとおりである。専用サーバーを `./gradlew runServer` で起動し、`run/eula.txt` で EULA に同意する。クライアントを `./gradlew runClient` で起動して入る。2つ目のクライアントは、別のユーザー名で入る(`./gradlew runClient --args="--username Dev2"` で起動できるはずだが、試していない)。両方で `/rtclock get` が同じ時刻を示すこと、サーバーで `/rtclock set 12:00` したあとに両方の空が正午になることを見る。

M4 は、いちばん不確かだった所要時間の計算から始めた。速度制御の再現(`TravelTime`)を、線路を走る実際の列車と比べて、5つの場合で tick 単位まで一致させた。比べる前の再現は、実際より0.5秒長く出ていて、それは駅で止まる点の見方の誤りだった。そのあと、ダイヤの JSON 形式を、読み書きと検証まで実装した(「ダイヤの JSON 形式」の節)。次に、ネットワークの書き出し(`/rtnetwork export`)を実装した(「ネットワークの書き出し」の節)。線路の探索は手で書いた線路網で、線路の上に並べた3駅ではゲームテストで確かめた。そのあと、Create Train Next の制限速度標識を、所要時間の計算とネットワークの書き出しに入れ、標識の下を走る実際の列車と4通りで比べて、tick 単位まで一致させた。最後に、ゲームテストで Create の曲線の線路(S字カーブと90度のカーブ)を組み、カーブを含む区間を実際の列車と比べた。カーブの上では、台車の車輪の位置を直すときのずれで到着が数 tick 動くので、差は0.6秒以内にとどまり、tick 単位では合わない。それでも、M4 の完了条件(差が数秒に収まる)は満たしている。そのあと、分岐と信号のある実際の線路でも確かめた。分岐を直進する列車と、進む向きの信号を通る列車は、計算と tick 単位で一致した。反対向きの信号については、駅と同じ辺の上にある場合を書き出しが見落としていたので、Create の探索に合わせて直した。M4 で確かめていないのは、信号待ちと複数の列車で、これは静的な見積もりの外に置いている。

M5 では、ダイヤのとおりに列車を動かす運行を、Create の時刻表に依存しない機能として実装した(「運行は、ダイヤのとおりに列車を直接動かす」の節)。ダイヤの形式には回送と、運用が車庫で始まり車庫で終わる規則を足して第2版にした。運用の割り当て、発車、遅れの回復は、周回線の実際の線路で、2本の列車を走らせて確かめた。完了の条件は満たしている。確かめていないのは、再起動をまたいだ運行、信号のある線路で複数の列車が同じ線路を走る運行、脱線である。

M6 では、ゲーム内の運行図を実装した(「運行図(M6)」の節)。終わった運用と中断した運用の実績を保存するようにし、画面を開いているクライアントに、ダイヤ、駅の間隔、実績を1秒ごとに送る。送る中身はゲームテストで、線の作り方は単体テストで確かめた。画面で計画と実績の線が重なって見えることも、実際のクライアントで確かめた。完了の条件は満たしている。

M7 では、ダイヤの編集ページを実装した(「ダイヤの編集ページ(M7)」の節)。ページは MOD の jar に入れて `/rteditor` で開き、同じファイルを GitHub Pages でも公開する。ゲームとは、クリップボード(`/rteditor copy network`、`/rteditor copy timetable` と `paste`)とファイルで受け渡す。誤りの検証はゲームの Java のコードを移し、共通のテスト用ダイヤで同じ結果になることを確かめた。ページの操作の関数だけで組んだダイヤが、実際の線路で各駅を時刻どおりに出ることを、ゲームテストで確かめた。そのあと、停車時間と最短停車時間を駅ごと、停車ごとに決められるようにし、ダイヤの形式を第3版にした。実際のクライアントから、クリップボードで貼り付けて走らせることは、まだ確かめていない。

M8 では、遅れが大きくなった列車を、運休してダイヤに戻す運転整理を実装した(「大きな遅れは、運休でダイヤに戻す」の節)。判断の規則は Minecraft に依存しない部品にして、規則を一つずつ外すと落ちる単体テストを書いた。実際の線路でも、大きく遅れた列車が駅で待ち、基準以内で出られる停車から出ること、空いた列車がない運用が遅れて出ること、遅すぎる運用が運休になること、遅く読み込んだダイヤの運用が遅れて出て駅で待つことを、ゲームテストで確かめた(Create 6.0.10-281)。完了の条件は満たしている。確かめていないのは、信号があり、ほかの列車も走る線路で待たせることと、実際のクライアントでの運行図の見え方である。

M9 では、列車がほかの列車を待つ待避と緩急接続を実装した(「待避と緩急接続(M9)」の節)。ダイヤは第5版にし、編集ページで待つ列車を決められるようにした。待つ規則は Minecraft に依存しない部品にして単体テストで確かめ、通過の検出と待ち方は、実際の線路でゲームテストで確かめた(Create 6.0.10-281)。完了の条件は、外側と内側に並べた別々の周回線と、待避線を組んだ1つの線路(信号つき)の両方で満たしている。そのあと、ゲーム内の運行図にも、待ちを編集ページと同じ点線の矢印で描くようにした。矢印の決め方は単体テストで確かめ、矢印が出ることは実際のクライアントでも見た。

M10 では、駅間ごとに列車が走る線路を決められるようにした(「線路のタグ(M10)」の節)。三つに分けて、すべて作った。一つ目の自前の経路探索は、Create の探索と同じ道を選ぶことを、実際の線路で Create の `findPathTo` と比べて確かめた。二つ目のタグのブロックと区間は、区間の辿り方を単体テストで、Create の線路グラフに置いた点から読むことをゲームテストで確かめた(Create 6.0.10-281)。三つ目のダイヤ第7版とタグどおりの経路は、単体テストとゲームテストで確かめ、待避線のテストを、両方のホームを A の名前にした形で通した(Create 6.0.10-281)。

M12 では、Create Train Next の上限を、所要時間の見積もりに入れている。標識の上限の駅をまたいだ持ち越し(運行の見込みと編集ページ)、ダイヤ第9版の列車の長さ、ネットワークの書き出し第5版の閉塞区間、ダイヤの列車を信号とともに走らせる再現(`Traffic`)まで作った。再現は編集ページの注意と、ドラッグと時刻の入力の制限にも使うようにした(`traffic.js`)。運行の見込み(待ち合わせ、遅れての出庫、遅れた列車を待たせる判断)にも使うようにして、M12 の段階はすべて済んだ。

次の一手は、編集ページを実際のクライアントから使って確かめること、GitHub Pages での公開、実機で確かめること(設定画面、複数人、本 MOD のないクライアントの接続)である。
